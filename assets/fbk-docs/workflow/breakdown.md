Use during breakdown. Divide the accepted specification into test tasks and implementation tasks in `tasks.json`, with the context each worker needs and an order in which the tests come first. Breakdown writes tasks only: no task runs, no test is written or run, and nothing is locked here. Closing breakdown reviews the plan. Implementation then runs the test tasks, the test checkpoint reviews and locks the tests, and the implementation tasks follow.
Before compiling assignments, read `repository-grounding.md` and `test-authoring.md` beside this file, and `test-regions.md` when the spec declares `test_regions`, unless their content is already in the current context; test tasks are planned here and written to that guidance in implementation.

## Compile bounded assignments

Read the accepted intent, design, specification, scope, and applicable sourced decisions. Map each material requirement and intent constraint to observable checks and the task responsible for them. Plan from each requirement's rule, not only its examples: the checks cover every clause of the rule. Keep this mapping in `tasks.json` through source references and verification descriptions; cite exact headings or lines where practical. Describe relevant failure cases and plausible incorrect behavior the checks should reject. Record consequential omissions or contradictions against the original authority before proceeding; task descriptions cannot redefine requirements.

Carry the spec’s settled conventions and deliberate departures to each applicable task through `acceptance_refs`, `input_refs`, and the existing description or verification fields as needed. Reference the authoritative decision instead of duplicating convention rules or asking workers to discover them again.

Read the existing files assignments will change or rely on. For a needed runtime value or signal, verify that the consumer can obtain it through the planned entry point; assign missing production or forwarding work and order dependent consumers after it. Cover the affected caller migrations discovered in repository searches, with ownership and checks for the complete agreed migration. Carry relevant source locations and observable wiring behavior in the existing task descriptions, references, and verification fields.

Split work where it reduces context load or clarifies ownership. Keep shared fixture and interface decisions explicit so independently authored tests agree. A fresh worker in implementation receives applicable source references, the observable outcome, owned files, dependencies, and verification responsibilities through `task-context`; it does not inherit the lead's transcript. Include relevant integration boundaries and intent constraints even when they cross a task boundary.

`tasks.json` is an array. Each task needs `stage` (`tests` or `implementation`), `id`, `description`, `files`, `depends_on`, `acceptance_refs` referencing both applicable intent and spec, and `verification` stating its definition of done: observable outcomes and plausible bugs its checks detect. Every task also needs a nonempty `check_expectations` array containing exact commands and expected exit codes; a test task may write `"nonzero"` for a check expected to fail. Link each requirement a task serves with an `acceptance_refs` entry naming its heading anchor in `spec.md`, such as `.fbk/example/spec.md#cancel-once`; such an entry must land on an item of the Requirements section, names no line number, and also counts as the spec reference. Every task links at least one requirement of its own unit, and every requirement is linked by at least one implementation task and at least one test task. A review-only requirement (one whose first line is `Checked by review: <reason>`) needs an implementation task but no test task; a test task may still link it. Every other requirement needs a test task: breakdown cannot opt one out of testing. A plan may therefore have no test task only when every requirement is review-only; implement then preserves the existing scoped tests, or runs with none, as `implementation.md` describes. A child unit's task may also link its parent's requirements; they reach the worker but do not count toward these rules. At launch the task context carries each linked requirement's section, its design choices' sections and their commitments' sections. Declare `consumes` for the file paths or patterns a task reads from other assignments; use an empty array when it consumes none. Consumed paths are read-only and must not overlap the task's owned files; owned files already carry their initial snapshot. `depends_on` orders tasks, without freezing all predecessor outputs. Add `input_refs` for relevant design, conventions, or additional reference context. A file listed in `input_refs` already counts as an input; do not repeat it in `consumes`. Use the references and verification description to identify relevant checks without a separate mandatory test-path list for every task. Existing references must resolve; a missing future input needs an ordered producer and must exist before its consumer launches. Breakdown close builds each task's context the way launch does and refuses the plan, naming each such task, when a task's traceability chain is over 64,000 characters or the rest of its context (its own fields plus the guidance) is over 16,000, or when a chain link misses its item. Split oversized tasks at coherent boundaries; do not remove required authority to meet the limit.

For each requirement it covers, a test task's `verification` names the plausible wrong implementation most likely to pass unnoticed and shows how the tests fail it: the input the tests use, what that wrong implementation produces on it, and the assertion that fails. A named wrong implementation that no test fails is a blocker at breakdown review and at the test checkpoint.

Use real project paths. A test task owns the tests it writes and any production file whose interface it must change so those tests build and load; list each such file in `files`, and declare each new path in the spec's `scope.json` `creates`. There is no separate field for placeholder files: a task carrying `stubs` is refused. Task commands may be focused subsets of the whole-unit checks declared in `scope.json`; they need not become whole-unit gates. The test checkpoint runs every command a test task names alongside the spec's whole-unit checks, and its reviewer reads each test's result in their saved output, so choose commands that report each test by name, as the spec's checks do (for example a runner's verbose mode). Implementation task checks must pass (exit 0) once that task is done, even while unrelated planned behavior remains red. Expected red belongs only to test tasks. A red check exits non-zero: declare its exact exit code, or `"nonzero"` to accept any failure, since only some runners give failing tests their own exit code (`go test` exits 1 for build and test failures alike, `cargo test` exits 101). A test task that preserves behavior already built declares exit 0. At the test checkpoint the reviewer judges from each check's output that it failed on an assertion about missing behavior, not on a build or load failure. A command that cannot be started at all, because it is missing or not executable, is a setup error, not red. Define these criteria here, before implementation; workers cannot replace them with easier checks. Test tasks may depend only on other test tasks; implementation tasks declare the test files and interfaces they consume separately from their ordering dependencies. Every test task finishes, and the test checkpoint locks the tests, before any implementation task starts. Refer to tasks by description when speaking with the human. Dependencies must be acyclic and files must fit scope. Tasks list existing paths or paths the spec declares in `scope.json` `creates`; a missing path the spec does not declare is refused. Firebreak judges each listed path by its kind on disk, or by its declared kind when it is new. An implementation task cannot own a scoped test: a file is checked as a file, so `pkg/foo.go` beside the test pattern `pkg/**/*_test.go` is fine, while a directory or wildcard is refused when it could hold a file matching the test patterns, even one that does not exist yet. A file with a declared test region may be owned by both a test task, which writes its region, and an implementation task, which writes the code above it. Before accepting breakdown, Firebreak validates the plan: each task's stage, listed paths, references, verification, ownership, and check expectations, the requirement links and coverage above (every problem named at once), the ordering of test and implementation tasks, and the task graph. It rejects unordered overlapping writers and unordered writer/consumer pairs, including paths that do not exist yet. Parallel workers need disjoint ownership and cannot modify another running task's inputs; they must also fit the human's concurrency constraints. A shared fixture or interface owner should finish before dependent test authors work against it. Verify that prerequisite through the first consumer’s actual execution route (for example pytest collection using the declared runner and configuration); ordinary Python imports alone do not establish that pytest can load the fixture.

Plan a refactor task after each wave of implementation tasks: an implementation task with `"refactor": true` that depends on every task in the wave and improves the structure of the code they built, under the locked tests. Breakdown close refuses a plan unless every path an implementation task owns is also owned by a refactor task that depends on it, listing the same path or a folder holding it. Give a refactor task the production folders the wave's tasks write in, so a boundary it extracts can become a new file there; where tests share a folder with production code, list the files instead. Split a wave too large for one worker's context by folder or module, never by implementation task, so each refactor sees every task's work in its part. It links no requirement: its worker reads the unit's accepted spec and design whole, which its packet names, so its acceptance_refs are the whole `prd.md` and `spec.md`. A requirement link it carries does not count toward an implementation task linking each requirement. Its checks are the whole-unit checks, which pass before and after it.

A documentation task's `check_expectations` include at least one command taken from the documented usage, run against the finished program with the exit code the documentation implies. A grep for a heading or phrase detects an absent topic but never a wrong example; only running what the document tells a reader to run shows that the documentation matches what the program does. The breakdown reviewer checks for this command as one of its obligations.

## Review and hand off

Before closing, read the plan as a whole: coverage of each behavioral requirement and of intent by test tasks, shared fixture and interface decisions, boundary and failure cases, and collaboration coverage. Check the named wrong implementations as the reviewer will: each requirement has one, and its input, wrong output and failing assertion show a planned test fails it. Resolve contradictory expectations before asking the reviewer to close breakdown. Keep selected follow-ups and unresolved questions in durable artifacts before resetting context.

```
fbk.py phase-close breakdown <unit>
```

Close validates the plan, then a fresh reviewer reads `tasks.json` against the accepted intent and specification: task outcomes, owned files, dependencies and ordering, coverage, check expectations, and whether the planned tests would fail each wrong implementation a test task names. No tests exist yet, so the reviewer judges the plan, not test code or check output. Fix demonstrated defects and close again. Firebreak accepts each task's definition of done and checks as part of breakdown; human approval to enter implementation covers the accepted plan, with no mandatory per-task approval.

Before giving the human an implementation command, retrieve continuation and verify the tasks, their references, and chosen follow-ups are recoverable. Start implementation only with applicable human authorization. The next session enters implement, where the test tasks run first; read `implementation.md` for that flow.
