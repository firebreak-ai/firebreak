Use for worker launch/return, continuation, or a planned context reset. Give the receiver the outcome, governing sources, owned files, dependencies, and required evidence.
A handoff points to original authority; it does not replace that authority with another agent's narrative.

## Continue or reset

Run `continuation <unit>` before handing off and after resuming, clearing, or compacting. Read its required sources and retrieve relevant omitted detail before acting. `continuation <unit> --section decisions|tasks|sources|pending|accepted_reviews` returns one complete selected section. SessionStart injects a bounded current-unit view and an index of other work. Pending questions must be checked against current sourced decisions before asking again.

Before giving the human a next-phase command, ensure the receiving session can reconstruct the required work from durable artifacts. Accepted review findings already live in the unit's state and are exposed through `accepted_reviews`, with their originating phase, source freshness, and each finding's digest and current disposition. A new phase having no reviews does not mean the previous phase had no findings. Suggestions remain advisory; distinguish chosen follow-ups, resolved or deferred concerns, and actual requirements. Persist chosen follow-ups and their source references through `suspend --reason` before a reset when they are not already recorded in governing artifacts.

On entering a phase, the packet's `undispositioned_suggestions` lists each accepted suggestion from earlier phases still awaiting the operator's disposition, with its digest, phase, index, title, and remedy kind; suggestions the author sorted before their phase was accepted are not listed. Group them by what they are about, put each group to the operator, write the operator's words to a source file, and record them with `decision-record <unit> --request <file>` carrying `dispositions` (see `decisions.md`). Fix-now work happens before this phase closes; a deferral names its owner; a decline carries the operator's reason in the decision text. The phase cannot close while any of these lacks a disposition, and the test checkpoint refuses to lock the tests while a suggestion whose remedy is a test lacks one, because nothing after the lock can add a test. Status shows the count as `undispositioned_suggestions`. Do not rely on the outgoing message or an undiscoverable scratch note. Retrieve the resulting continuation to verify the handoff, then check current status before recommending the next phase.

Use fresh workers for independent tasks and repairs. At an accepted phase boundary or after substantial rework, finish active workers, persist the pending work with `suspend <unit> --reason "<next action or unresolved decision>"`, then start a fresh session with the unit name. Resume with the current phase skill and continuation. Clear only after the needed source decisions and work state are durable. Firebreak supplies reconstruction; it does not issue an unsolicited interactive `/clear` during active work.

## Launch a worker

Compile or supply each task's applicable acceptance references and supporting inputs, including the spec’s settled convention decisions and their governing sources. The worker receives the task description/outcome, source references, owned files, input revision, and dependency outputs. Provide the unit and task in the spawn prompt; omit the authoring transcript and prior reviewer discussions.

`task-context` and an assigned worker's SubagentStart packet include the shared repository-grounding instructions. Read and apply the packet’s governing references and shared guidance before task work; another read of the same guide is unnecessary. For design or spec authoring delegated without a task assignment, supply the applicable phase reference under the resolved Firebreak installation so the worker receives its authoring instructions. Preserve concrete producer, value, and consumer source references when handing off changed shared behavior.

```
fbk.py task-start <unit> <task> --worker <agent-id> --acceptance-refs .fbk/<unit>/spec.md --input-refs .fbk/<unit>/spec.md docs/conventions.md
fbk.py task-context <unit> <task>
```

Use the actual worker identity. If the host supplies it only at SubagentStart, that hook provides the identity and routing context. The lead or worker records the assignment before file writes, then the worker reads `task-context`. Workers use the owning session identity on workflow commands; the lead enters and closes phases. A worker can explicitly supply `--outcome` when the accepted task description needs a more concrete completion target.

Task-start runs only in implement, against the accepted breakdown; breakdown writes tasks and starts none. Test tasks start while the unit is writing tests, and implementation tasks once the test checkpoint has locked the tests. Task-start requires applicable acceptance sources, completed scheduling dependencies, and no conflicting active writers or consumers. `consumes` declares file inputs separately from `depends_on`; packets carry their current hashes. Source references added with `input_refs` receive the same protection and need not be repeated in `consumes`. Missing future inputs are allowed in the plan only with an ordered producer; all references and consumed files must resolve at launch. The worker identity is the subagent's agent id; task-start refuses the lead's session id. The packet's `traceability` entry carries the chain behind the task: the section of each requirement its `acceptance_refs` link by anchor, the sections of the design choices those requirements link, and the sections of the commitments behind them, each once, a parent unit's included; a requirement link added with `--acceptance-refs` at launch must land on a requirement and joins the chain. Breakdown close and launch are refused, naming the task, the document and the link, when a link the chain follows misses an item of the correct section, for example after an upstream heading is renamed, or lands in a design file of an ancestor unit that is routed to skip design. Every document the chain is read from binds the assignment, so changing one makes the context stale. The traceability chain may be at most 64,000 characters, and the rest of the packet (its task fields and guidance) at most 16,000; each limit is checked on its own, at breakdown close and again at launch, so the lead narrows the task instead of silently dropping required context. An oversized chain's refusal names the task, each linked requirement's chain size, and the five largest linked sections; split the task so each part links fewer requirements, or tighten an oversized item section in its accepted document. An oversized rest's refusal names the task and its five largest fields; shorten the task's own fields or split the task. An unexpected external input change is flagged as interference and requires refreshing and revalidating the affected running task. Managed scheduling and write hooks prevent this conflict during normal operation. Completed test assignments retain their recorded red checks when a later implementation task fills in the interface they prepared; a future consumer receives current source hashes. Governing intent/spec changes still invalidate assignments. An assignment binds its own `tasks.json` entry plus the entries of the tasks it depends on or consumes files from; editing an unrelated task leaves it valid, while breakdown acceptance still covers the whole plan. Use `task-cancel <unit> <task> --reason "<why this assignment ended>"` after stopping a stale or interrupted worker, then relaunch against current inputs. For a completed stale assignment, use `task-start` again, inspect the existing work, rerun its checks, and submit a fresh `task-finish`. `continuation` lists these blockers, a stale completed test task keeps the unit writing tests, and nothing restamps old task evidence.

Use narrow file paths or disjoint directory prefixes for parallel ownership. Glob patterns whose static prefixes overlap run sequentially, because new files could otherwise fall under both assignments.

## Return evidence

Write a repository-relative JSON result file:

```json
{
  "outcome": "Cancellation releases its resource exactly once.",
  "changed_files": ["src/cancellation.py"],
  "checks": [{"argv": ["python", "-m", "pytest", "tests/test_cancellation.py"], "exit_code": 0, "evidence": "Repeated cancellation and release failure cases pass."}],
  "unresolved": []
}
```

Run `task-finish <unit> <task> --result <result-file>`. The runtime compares the declared changed files with actual owned-file changes and checks the launch inputs and dependency outputs. Changes are measured from the snapshot `task-start` took, so an edit made before the assignment was launched is already in the snapshot and is declared as nothing; a mismatch names the snapshot time, the declared-but-unchanged paths, and the changed-but-undeclared paths. Report every command from the assignment’s accepted `check_expectations`; extra diagnostic checks are allowed but cannot replace a required command. The runtime executes the required checks independently and records `verified_checks`; worker-reported success alone cannot complete a task. Checks run outside the project lock so independent workers can continue. Before committing, Firebreak reloads current state and revalidates the same assignment, governing inputs, and owned outputs; changed evidence requires a fresh return. Undeclared checks must pass. Expected red is allowed only for test tasks and must report the actual failure evidence. A `"nonzero"` expectation accepts any failing exit code and an integer must match exactly; the actual exit code is recorded either way. A check command that cannot be started is refused as a setup error rather than counted as red. Unexpected outcomes, omitted expected checks, or unresolved issues leave the task needing attention. The task’s `verification` is its reviewed definition of done. A focused implementation check can pass while other planned work remains red; implementation close independently runs the whole-unit checks declared in scope. Final close rejects unfinished, stale, or subsequently changed task results unless a completed dependent task accounts for the later owned-file changes.

Keep the result within 16,000 serialized characters. Store full logs in runtime artifacts and cite concise evidence in the return.
