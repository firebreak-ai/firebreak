Use during implementation. Implementation runs the whole plan that breakdown wrote: the test tasks write the tests, the test checkpoint reviews and locks them, and the implementation tasks then deliver the accepted behavior against those locked tests. Read each task's intent, requirement, test, and convention references before its work starts. Apply the spec's settled conventions and deliberate departures using the repository-grounding discipline below.
Launch every task, test or implementation, in its own subagent; read `handoffs.md` beside this file for launch and return. Test-task workers also receive `test-authoring.md` through `task-context`, and `test-regions.md` when the scope declares `test_regions`.
Before editing, read `repository-grounding.md` beside this file unless its content is already in the current context, including through `task-context`. Use the actual entry point and affected consumers to verify changed wiring and complete the agreed migration before returning the task.

## Enter implement

Record approvals only when the human actually grants the crossing. Do not invent approval words or treat host permission mode as consent. Existing authorization applies when it covers this exact work; do not repeatedly ask for the same decision.

```
fbk.py approve <unit> start-implementation --phase implement --reason "<human's words>"
fbk.py phase-enter implement <unit>
```

Entering implement needs no locks. Firebreak records the writing-tests baseline whenever the unit begins or returns to writing tests: on the first entry into implement, when an unlock is approved, when a governing decision is recorded that makes the checkpoint's acceptance out of date (at the moment it is recorded, including when an edited decision source had already made that acceptance out of date), and on re-entering implement after breakdown or an earlier phase was reopened, or a contradiction repair invalidated breakdown. The baseline is a saved copy and fingerprint of every scoped test file and every production file in scope, kept in the unit's `writing-tests-baseline/` folder, so code built before it counts as already there. Relaunching or cancelling a task and a rejected checkpoint never re-record it, so an earlier change stays visible to the checkpoint.

Implement has three stages that Firebreak works out from the recorded facts; `status` and `continuation` report the current one under `test_preparation`:

- **Writing tests**: some test task lacks a completed, current run, or a locked test has an approved unlock outstanding. Test tasks run; no implementation task starts.
- **Ready for checkpoint**: every test task has a completed, current run, and any outstanding unlock has been reworked. Run the test checkpoint. Relaunching a test task returns the unit to writing tests.
- **Writing code**: the test checkpoint locked the tests, its acceptance still matches the current tests, plan, and governing decisions, and no unlock is outstanding. Implementation tasks run; test tasks are refused, and no worker writes any path matching the scope's test patterns, locked or new, or changes a test region.

## A plan with no test task

Breakdown accepts a plan with no test task only when every requirement is review-only. Such a unit takes one of two outcomes, decided when the baseline is recorded on entering implement and reported by `status` and `continuation`. A resume or an implement reopen keeps it; after a breakdown-or-earlier reopen, or a contradiction repair that invalidates breakdown, it is decided again at re-entry. In both, an unlock is refused, since no test task exists to rework a test: reopen breakdown and plan a test task instead.

- **Preservation**: scoped tests exist (whole test files, or test regions holding tests). The unit is ready for the checkpoint at once. This preservation checkpoint needs every whole-unit check to pass; a failing check is refused, and the remedy is to fix the cause or reopen breakdown to plan test tasks. A scoped test that differs from the writing-tests baseline is refused, since no test task could have changed it. The reviewer reads the production files the implementation tasks own, judges whether the scoped tests protect the code the unit will change, and confirms from the saved output that every scoped test ran and passed. On a pass every scoped test locks, and the unit writes code as usual.
- **No tests**: no scoped test exists. The unit writes code from the start, with no checkpoint and no lock, and `test-checkpoint` is refused. Firebreak records the empty test inventory, and task start, task finish (also after its checks run) and implementation close refuse while any scoped test exists, naming it: remove it, or reopen breakdown to plan a test task for it. The write hook still refuses every scoped test path. Implementation close needs no checkpoint or lock for this unit, and implement's review compares the delivered code with the writing-tests baseline.

## Write the tests

Run the test tasks in waves that respect their `depends_on` order, one subagent per task. A test task's worker writes its declared tests and makes the smallest change to the production files it declares that lets the suite build and load against the planned interface: new or changed signatures, types and fields, and the caller adjustments needed to build. Existing code keeps its current behavior, and new code does nothing meaningful. The worker writes only the files its task lists. Each test task's `task-finish` runs its declared checks itself and completes the task only when each meets its expected exit code; a check expected to fail exits non-zero, and one preserving behavior already built exits 0. After the checkpoint has accepted the tests once, a test task whose tests are all unchanged since that acceptance completes even when its checks now pass, because code built since does the right thing; its return is marked as carrying that acceptance's red forward (`carried_forward_red`), and the checkpoint reviewer judges it. Only that one extra outcome is allowed: a check expected to pass must still pass. Correct code is never undone to recreate red. Keep those completion criteria fixed; additional diagnostics do not replace them. A test task that finds a test outside the scope broken reports the scope gap instead of editing it.

## The test checkpoint

The test checkpoint is the review that accepts the authored tests and locks them; it is the only way tests are locked. Run it when the unit is ready for the checkpoint and no task is running:

```
fbk.py test-checkpoint <unit>
```

The checkpoint compares the current tree with the writing-tests baseline. Tests that differ from the baseline were changed by test tasks; the rest are untouched. A production change outside every test task's declared files is refused before any check runs, naming the files: restore them from the baseline copies, or rework the change through a test task that declares them. A change to a production file's executable bit, or to the target a symbolic link points at, counts the same way: an undeclared one is refused, so a test task that needs one declares the file, and the reviewer's diff shows it. Code built before the latest baseline is inside it. An implementation task that was running when the baseline was recorded may finish afterwards: its own files, as that run's completed, verified return records them, are not counted against the test tasks, even a file it changed and then restored after the baseline caught it mid-change, or a file it created after the task started and deleted again after the baseline caught it. The reviewer sees those files listed as verified implementation work, not as test-task diffs. When a test task later changes a file that task also changed or deleted, even back to its baseline content, the reviewer sees only the test task's change, against what the implementation task returned. Any other change, including one by a task cancelled after the baseline, is refused. A unit that entered implement before Firebreak recorded baselines has none to compare with and cannot recover one, so the checkpoint refuses it; move the unit under `.fbk/archive/` and redo it as a new unit.

The checkpoint then runs every whole-unit check declared in `scope.json`, plus each command a test task expects an outcome from, and keeps going after a failure. The spec's whole-unit checks report each test by name, so the saved output shows every test's result. Each check's complete output is saved in the unit's `check-output/` folder, and its fingerprints go into the checkpoint's evidence. Each check must meet every test task's expected outcome, and at least one must fail, unless every test task expects its checks to pass because the tests preserve behavior already built.

After the checkpoint has accepted the tests once, Firebreak cannot tell which tests a check covers, so a later run makes no red demand: it still runs and saves the whole-unit checks and each test task's commands, but holds none of them to an expected exit. A test task that owns an outstanding unlocked test runs the approved rework commands instead, and those must meet their expected exits. The reviewer is also told each unlocked test's approved outcome and which tests each rework command covers, since one command's exit cannot show a reversal among the tests it covers. Before the run replaces `check-output/`, Firebreak copies the previous acceptance's output into `accepted-check-output/`. The reviewer is told which tests are unchanged since that acceptance, and its saved output is required reading: an unchanged test keeps its earlier red; a new or changed test for behavior not yet built needs fresh red; a changed test that passes because the code already does the right thing is accepted when the reviewer judges that it preserves that behavior. These folders belong to Firebreak: Git ignores them and the write hook refuses edits to them.

A fresh reviewer then reads the tests, the saved output, and each declared production change as a diff against its baseline copy, and asks whether the tests are useful: would they catch code that departs from the design. From the saved output it confirms that each changed test expected to fail fails on an assertion about missing behavior and that each untouched scoped test passes or carries earlier red forward. A build or load failure, a skipped test, or a scoped test missing from the output is a blocker, and so is a declared production change that adds behavior. For each plausible bug a test task's `verification` names, it judges whether a test catches it, and where reading is not convincing it tries that wrong implementation in a disposable workspace. A named bug no test catches is a blocker, and so are wrong or vacuous tests.

On a pass, Firebreak records the checkpoint's evidence and locks exactly the reviewed tests in the same step, saves a copy of each locked test in the unit's `locked-tests/` folder, and the unit moves to writing code. A pass needs no human approval and no phase observation; implement stays open. On blockers, nothing locks: relaunch the test task that owns the faulty tests, which returns the unit to writing tests, then run the checkpoint again. The checkpoint has its own round budget, separate from implement's. When it runs out, status reports human review for `test-checkpoint`, and the usual escalation applies: `extend-review test-checkpoint <unit>`, `recover-close test-checkpoint <unit>` for an interrupted run, and `approve <unit> close-over-findings --phase test-checkpoint` to accept over findings. A suggestion whose remedy is a test, from the checkpoint or any accepted phase, needs a recorded disposition before the tests lock. Once the checkpoint has accepted the current tests it refuses to run again; it runs again only after an unlock, a breakdown-or-earlier reopen, or a new governing decision makes that acceptance out of date. Reopening implement keeps it. A failed run then withdraws the earlier acceptance.

## Write the code

In writing code, run the implementation tasks in waves that respect their `depends_on` order, one subagent per task. Read each task's reviewed definition of done (`verification`) and required passing commands (`check_expectations`). Keep those completion criteria fixed; additional diagnostics do not replace them. A focused task check may pass while unrelated planned work remains red. Whole-unit success is required at final closure. Fill the interfaces the test tasks prepared with behavior that satisfies the locked tests and governing contracts. Do not change tests to make production code pass. Preservation work has an explicit reason and existing regression evidence instead of an artificial red failure.

A refactor task (marked `refactor`) runs once the tasks it depends on are done. Its worker receives `refactor.md` beside this file in its packet, reads the accepted spec and design files the packet lists under `rules_sources`, changes only production code, and returns its review as the task's outcome; implement's close review checks each review against the delivered code. An implementation task redone after a refactor task completed makes that refactor stale: run the refactor task again before close.

To correct a locked test after discovering the contract was wrong, the human approves an unlock that names the tests and how they will be reworked. Firebreak sees only exit codes, so the approval states, for each named test, whether its corrected form is expected to fail (the behavior is not built yet) or pass (the code already does the right thing), and gives the commands the rework runs, each listing the named tests it covers. Write that as a request file:

```json
{"expected": {"tests/test_cancellation.py": "fail", "tests/test_release.py": "pass"},
 "commands": [{"argv": ["pytest", "tests/test_cancellation.py"], "tests": ["tests/test_cancellation.py"]},
              {"argv": ["pytest", "tests/test_release.py"], "tests": ["tests/test_release.py"]}]}
```

```
fbk.py approve <unit> unlock-test --phase implement --tests tests/test_cancellation.py tests/test_release.py --request <file> --reason "<human's words>"
```

Every named test needs a stated outcome and at least one command covering it, and a command may cover only named tests. A command's expected exit is worked out from its tests: zero when all of them are expected to pass, non-zero otherwise. Each named test must belong to a test task; if none owns it, reopen breakdown and add a test task that does, then re-enter implement, run that task, and pass the checkpoint, which locks the test again. A command repeated from another outstanding unlock is refused when the two would need different exits.

The unit returns to writing tests: the checkpoint's acceptance is cleared (its rounds and budget stay), and the writing-tests baseline is recorded again over the code built so far. Relaunch each test task that owns a named test; its run uses the approved commands covering its tests in place of the ones in `tasks.json`, which stays unchanged, and `task-finish` holds them to their expected exits. An implementation task already running keeps writing its own files, but no new one starts. Once every test task that owns an unlocked test has completed a run since the approval, the unit is ready for the checkpoint. Finish or cancel any running task, then run `test-checkpoint` again: on a pass it re-locks the tests and clears the unlock. A locked test the unlock does not name must not change; task start and finish refuse while one differs, and the checkpoint refuses to lock over one. A red check exits non-zero; the reviewer confirms from its output that the tests failed on assertions about missing behavior, since build, import, collection and syntax failures are not meaningful red.

## Locked tests at task boundaries

A test region (the end of a source file, declared in the spec's `test_regions`) counts as a scoped test and the code above it as a production file. Each rule here applies to the part a change touches: the baseline, the checkpoint's changed and untouched tests, the lock, and the boundary checks compare the region alone, and the code above it is compared as production code. The reviewer still sees the file whole. For an Edit or Write of such a file the write hook works out the file as it would be after the change; it refuses the change when it cannot work that out (the text to replace is absent or not unique, the file cannot be read, or the tool is not Edit or Write).

The write hook stops edits to locked tests, but a shell command can still change one. So every task start and every task finish compares each locked test with its lock; a finish checks again after its checks have run. A test named in an outstanding unlock is skipped, since its rework is expected. A new test file is not a lock change. When a locked test differs or is missing, the start or finish is refused, naming the files and showing each one's diff against its saved copy. A refused finish leaves the task running. Firebreak records the refusal as a lock violation, naming the task and every task running at that moment, because any of them may have made the change.

Restore the locked content with:

```
fbk.py restore-locked-tests <unit> --tests <path>...
```

It replaces each named file with its saved copy, recreating a deleted file. For a test region it replaces only the region and keeps the current code above it byte for byte; when the start line is gone, it appends the saved region. It accepts only locked tests that differ from their locks, and refuses a test with an outstanding unlock: that test is reworked through its test task instead. If a locked test is wrong rather than damaged, ask the human for an unlock as described above.

The saved copies live in the unit's `locked-tests/` folder, which Git ignores and the write hook refuses, like the other folders Firebreak keeps. Every lock by the checkpoint replaces them with the newly locked content; if the new copies cannot be saved, nothing is locked and the earlier copies stay. A finish whose checks time out or fail to run still compares the locks, and reports a changed locked test alongside the failure. They are deleted when implementation closes, and when a breakdown-or-earlier reopen or a contradiction repair clears the locks. Before deleting them, Firebreak sets aside a copy checked against the locks, and removes it only once the close, reopen, or repair is saved. A failure before that save refuses the operation and keeps every copy recoverable: fix the cause and retry, or, after an interrupted close, run `recover-close implement <unit>`, which puts the copies back. A failure to remove the set-aside copy after the save does not undo the operation; its result reports `cleanup_failed`, and the next copy save or `recover-close` deletes the leftover. Recovering after an accepted implementation close deletes any copies left, live or set aside, rather than restoring them, since the close no longer needs them.

## Reopen

Reopening breakdown or an earlier phase clears the test locks, their saved copies, any outstanding unlock, and the checkpoint's acceptance, and resets the checkpoint the way a later phase is reset: a new review generation, and a fresh round budget of three more rounds. When the unit enters implement again, the writing-tests baseline is recorded over the code already built, the test tasks run again, and the checkpoint runs again, carrying red forward for tests unchanged since its earlier acceptance. A contradiction repair that invalidates breakdown replans the unit the same way: it clears the locks, their saved copies, any outstanding unlock, and the checkpoint's acceptance. Reopening implement alone keeps the locks, the acceptance, and the baseline. The reopen itself compares each locked test with its lock: when all match, it saves their copies again; when one differs, the reopen is refused, naming it, and the file must get its locked content back, such as from Git, before implement can be reopened.

## Close

Implementation closes only on tests the test checkpoint locked, with that acceptance still current and no unlock outstanding, except in the no-tests outcome above. Close rejects changed, missing, newly untracked, or still-unlocked tests. Passing the suite is necessary but does not establish maintainability; the reviewer must inspect behavior, error paths, coupling, duplication, and unnecessary complexity. Implement's review compares the delivered code with a baseline: before implement's first acceptance, that is the accepted test checkpoint's reviewed tests and saved check output.

`phase-close implement <unit>` runs every check in order, stops on a failed check, and accepts only current evidence. Implementation uses a fresh headless Claude reviewer with read-only tools, and so do intent and breakdown when no review plan is recorded. In those cases a configured second reader adds an independent candidate set and an adjudication pass; failure of that optional reader is disclosed. A recorded single or council plan, required at design and spec, runs instead. A missing or invalid required result fails the close.

No test checks a review-only requirement (one the spec marks `Checked by review: <reason>`), so the implementation review assesses each one: it is told each such requirement with its reason and returns a verdict, met or not met, with evidence, and a remedy when not met. A review result that leaves one out, repeats one, or names a requirement that is not review-only is refused like any malformed review. With a second reader, both readers assess every one; when they agree on each verdict and report no findings, the agreed verdicts stand, otherwise the adjudication pass assesses each requirement again after reading both readers' verdicts, and its verdicts stand. Each standing not met verdict becomes one blocker at the requirement, so close stops until the work meets it; these blockers are Firebreak's own and do not count toward the reader's limits on findings. The breakdown and test checkpoint reviews are also told the review-only requirements, and hold only behavioral requirements to their test demands. The standing verdicts are kept with the round's result.

Read `retrospective.md` and append your own observations throughout implementation, preserving original evidence while it is available. After acceptance, record the required phase observation before declaring completion, including a clean outcome when appropriate. Run improvement analysis within the user's requested scope; an ordinary successful close does not require inventing an improvement proposal.

## Changes after acceptance

`status <unit>` reports `acceptance_drift` against the last managed implementation acceptance: modified, deleted, unavailable, and newly scoped files, plus candidate tests outside its declared scope. `continuation` carries the same report; a bounded packet retains counts and a status retrieval command. The original acceptance and test locks remain unchanged. A standalone review or a later green test run does not renew managed acceptance.

For new acceptances, Firebreak records the accepted scope and a conventional test filename inventory, so existing unrelated candidates are not described as later additions. Older acceptances lack that inventory: their outside-scope candidates have an unknown introduction time. Discovery examines declared test parents and conventional `tests`, `test`, and `__tests__` directories, recognizing Python, Go, Java, C#, and `.test.*`/`.spec.*` naming conventions; it excludes caches and symlinks. This is a prompt for scope review, not authoritative test-runner collection, and cannot identify arbitrary custom test filenames.

Review the reported changes against intent and the accepted scope. Obtain human approval for reopening the earliest affected phase (`approve <unit> reopen --phase <phase> --reason "..."`), then use `phase-close <phase> <unit> --reopen --reason "..."`. Obtain any required approval for scope or locked-test corrections and re-close affected phases with current evidence. Do not expand scope, rebind hashes, or relock tests merely to suppress a drift report. When recording a retrospective observation, cite the original closed event and the changed file evidence; the status comparison is a current observation, not a reconstructed history of who changed each file or why.
