Author tests against the assigned observable behavior and its original intent and requirement sources. Use the task's references and verification responsibilities.

Exercise the real production interface and real collaborator behavior where feasible. For existing code, use its actual callable boundary. For planned code, test the accepted observable contract through the entry points the design names, one per behavior; keep private implementation choices open. Tests add maintenance work and earn it by catching bugs, so use the fewest tests that together catch the plausible wrong implementations; spec examples become those tests. Test behavior, not implementation, so the code can change and grow: a different correct implementation passes every test, and each plausible wrong one fails at least one. Keep fixtures internally consistent and assert observable requirements rather than reproducing the production algorithm, checking values the test just assigned, or mocking away the behavior under test. Check a chosen detail such as a format or a message in its own test, apart from the behavior checks, so changing it touches one test.

Choose fixtures and assertions that distinguish plausible wrong behavior from the required behavior. For example, to reject accidental tilde expansion, give literal `~` and the home directory different contents and assert which one is used; identical failures establish neither choice. A “detects” description alone is not evidence. Before reporting, run each wrong implementation the task's `verification` names against your tests in a disposable workspace outside the repository, and report the test that fails it; probe any other uncertain distinction the same way.

Test tasks run in implement, before the test checkpoint. For the production files listed in the task's `files`, make only the smallest change that lets the suite build and load against the planned interface: new or changed signatures, types and fields, and the caller adjustments needed to build. Existing code keeps its current behavior and ignores new inputs; a new module gets only its importable interface and minimum structural definitions, doing nothing meaningful. A stub returns a value no planned test expects; when a planned test expects the natural default (zero, empty or none), return something else, so each planned red fails on an assertion about missing behavior. Assert the eventual contract, with missing behavior left unimplemented. Existing-source behavior changes and extraction belong to implementation tasks. Surface an existing-interface testability problem through the handoff rather than replacing the real interface with a fake or relaxing the expected failure.

Run the declared checks and inspect the failures. Expected red must demonstrate missing intended behavior with imports, collection, dependencies, and syntax working. Mechanically a red check exits non-zero, but a non-zero exit alone does not establish behavioral red: the output must show the tests failing on assertions about missing behavior, not on a build or load failure. Preserve the actual exit code and concrete failure evidence; do not wrap a failure to manufacture success. For assigned preservation checks, verify that the existing required behavior passes. The test checkpoint reviewer reads the saved output of every check, so each test's result must appear in it by name; a skipped test or one missing from the output is a blocker there.
