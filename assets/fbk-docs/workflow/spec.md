## Scope and verification

`scope.json` names repository-relative paths, directories, or globs. The shell is never used to interpret a check: each check is an argument array executed in the repository root.

```json
{
  "sources": ["src/cancellation.py"],
  "tests": ["tests/test_cancellation.py"],
  "docs": ["docs/cancellation.md"],
  "context": ["docs/conventions.md"],
  "creates": ["src/cancellation.py", "tests/test_cancellation.py"],
  "checks": [["uv", "run", "pytest", "-v", "tests/test_cancellation.py"], ["uv", "run", "pytest", "-v"]]
}
```

Features require nonempty sources, checks, and tests or `test_regions`. Each check in `checks` is a whole-unit check and must report each test by name, for example through the runner's verbose mode (`pytest -v`, `go test -v`): the test checkpoint saves every check's complete output, and its reviewer confirms each test's result from that output, treating a test absent from it as a blocker. Project units can declare empty arrays. External symlink targets are rejected; generated dependency/cache directories are excluded. Prefer exact files or narrow globs; include affected existing tests and durable docs. Scope changes after spec acceptance require reopening spec. Do not include workflow control records in scope.

Declare every path the unit creates in the optional `creates` array: an entry ending in `/` is a directory, any other entry is a file. Firebreak never guesses a path's kind from its name. Spec close refuses an entry that already exists, falls outside the sources, tests, and docs, or sits under a missing directory that is not itself declared. Breakdown tasks may list only existing paths and declared ones. The declared paths follow the design's module layout. Extend existing files, modules, and functions where they fit, and add a new one only where the design calls for a new responsibility. Never create a parallel file that holds an existing file's responsibility; the spec review treats one as a blocker.

Tests default to whole files matching `tests`. When the project keeps unit tests at the end of the source file they test, declare them in the optional `test_regions` array instead: each entry is `{"files": [<paths or globs>], "start": "<regular expression>"}`. A matching file's test region starts at the first line the expression finds, without its line ending, and runs to the end of the file; the code above it is production code. For example `{"files": ["src/*.rs"], "start": "^#\\[cfg\\(test\\)\\]$"}` for Rust's `#[cfg(test)] mod tests`. Choose an expression that matches only the line that opens the test block: the first match starts the region, so a line in the code above that also matches would move the region, and an edit that adds such a line is refused as a change to the tests. Keep each region-bearing file in one line ending with no UTF-8 byte-order mark: the write hook refuses edits to a file with mixed line endings or a byte-order mark, because it cannot tell what the editing tools would write. Every region file must also be matched by `sources` and must not be matched by `tests`, and a file may be matched by only one entry. A feature may declare `test_regions` with no `tests`. Tests interleaved with code throughout a file, such as Zig `test` blocks or D `unittest` blocks, are not supported: the unit moves those tests into an end-of-file region or into separate test files, and the spec review treats an interleaved layout as a blocker.

The optional `context` array names authoritative repository conventions and shared contracts. These inputs are required and revision-bound from spec onward. Keep files intended to change during implementation in sources/tests/docs; use context for governing inputs whose change warrants revalidation.

Check that observable contracts and verification preserve the accepted responsibility boundaries. A shared policy needs examples that would detect its consumers drifting; separate happy paths alone may miss that defect. Flag specifications that recreate independent policy owners or require conflicting behavior across shared interfaces. Do not prescribe private helper tests or module splitting without a concrete contract or maintenance reason. Correct the current spec when it departs from a sound design; reopening design is warranted only when the correction changes an accepted architectural decision or contract.
