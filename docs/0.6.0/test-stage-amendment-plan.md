# Test-stage and traceability amendment

Branch: `develop/0.6.0-astra`. Written 2026-10-22. Decisions settled with the operator one question at a time on 2026-10-21 and 2026-10-22, then revised over three review rounds by GPT-6 Astra and Fable; the operator settled each gap those reviews found that the decisions did not already answer.

## Why this amendment exists

A live Realmind unit running installed 0.6.0 showed that the 0.6.0 rewrite reshaped two parts of the operator's design without a recorded decision.

- **Where tests are written.** 0.5.2 breakdown wrote paired test and implementation tasks; `/fbk-implement` ran the test waves, then the implementation waves. 0.6.0 runs test tasks during breakdown and locks them at breakdown close (`1e2bb85`, 2026-09-13). No decisions-log entry or plan decision calls for the move.
- **Traceability.** The operator asked for each task to carry its requirements, the design choices behind them, and the commitments behind those. 0.6.0 links whole documents only.

The same unit exposed three mechanical gaps that follow from the move: a test task cannot change an existing production file, so a test for a changed interface cannot build; the lock covers every scoped test while implementation tasks may own those files; and lock changes made through the shell surface only at implementation close.

The intended flow: breakdown writes test tasks and implementation tasks and stops. Implementation runs the test waves in subagents, reviews and locks the tests, then runs the implementation waves in subagents. The test author writes tests and only the interface placeholders they need; the implementer writes code and never changes tests. Every task knows what it is building and why, through the chain from requirement to design choice to commitment.

Scope is limited to these issues. Other divergences from operator intent wait for the Realmind retrospective.

Threat model (operator, 2026-10-22): Firebreak defends against agent mistakes and shortcuts, not adversarial code. Test or check code that deliberately manipulates the filesystem to fool Firebreak (planting symlinks, relocating its record folders) is out of scope, consistent with 0.6.0's stance that shell edits are a documented prevention gap. Projects may use symlinks and similar features for legitimate reasons, and hardening against them could break those projects; defending against malicious code, if wanted, gets a separate dedicated security pass. Reviews of this amendment are told so.

## Decisions

1. **Implement has stages, derived from recorded facts.** `/fbk-implement` stays one phase so the lead keeps its context across stages. The state machine derives the stage the way it derives phase status, with no agent-maintained stage field:
   - **Writing tests**: the checkpoint has not accepted the current tests, or a locked test has an approved unlock outstanding.
   - **Ready for checkpoint**: every test task in `tasks.json` has a completed, current run. Test tasks may still be relaunched for rework, which returns the unit to writing tests.
   - **Writing code**: the checkpoint has accepted the current tests and they are locked.

   Task start, the write hook, the checkpoint, and implementation close read the derived stage. Stage completeness walks every task declared in `tasks.json`, so a test task that never ran keeps the unit in writing tests. Entering implement needs no locks. A separate phase between breakdown and implement was rejected because it splits the lead's context and contradicts the operator's description of implementation.

2. **The test checkpoint is a full review gate that locks on pass.**
   - Its review record is `record["phases"]["test-checkpoint"]`, created when the unit is initialized, with the same shape as a phase entry (rounds, round budget, generation, pending operation, accepted evidence). It is not in the phase list, has no slash command, needs no human approval on pass, and records its own pass event rather than a phase `closed` event, so it requires no phase retrospective observation. Every existing guard that walks the phase records sees it.
   - Its revision digests the accepted breakdown revision, the fingerprints of every scoped test file and test region, and the governing decisions that apply to implement (process and disposition records excluded), so a newly recorded governing decision invalidates an earlier checkpoint review. Production code is excluded, so writing code never makes an accepted checkpoint stale. A current checkpoint is one whose revision matches and whose locks verify.
   - It uses the same fixed reviewer as breakdown and implement (the native reader plus the optional configured second reader). One command runs it; a pass captures red evidence and locks the tests in the same step. Blockers keep the unit in writing tests, and the lead reworks through test tasks.
   - Escalation matches phase close: budget extension, recovery of an interrupted checkpoint, approval over findings, and disposition of test-remedy suggestions all address the checkpoint. Its budget is independent of the implement review's.
   - Its purpose, in the operator's words: ensure the authored tests are actually useful and should be expected to detect bugs where the code deviates from design; wrong or vacuous tests are rejected and reworked. This restores what the pre-0.6.0 test reviewer did.
   - Implementation close requires a current accepted checkpoint, and the checkpoint's accepted snapshot, including its saved output, is the implement review's baseline test contract.

3. **What a test task delivers.**
   - Each test pins observable behavior a specific requirement demands, and through that requirement traces to design choices and commitments.
   - Against the placeholder code it fails because the required behavior is missing: not from a build or load failure, and not by passing by coincidence with a placeholder's empty result.
   - A plausible wrong implementation that violates the design fails it. The task's `verification` field names the plausible bugs its checks detect; each named bug has at least one test that catches it.
   - The task may make the smallest production change that lets the suite build and load against the planned interface: new or changed signatures, types and fields, and the minimal caller adjustments needed to build. Existing code keeps its current behavior and ignores new inputs; new code does nothing meaningful. The task declares every production file it touches in its `files`. The separate `stubs` field is retired.
   - Firebreak records a baseline whenever the unit begins or returns to writing tests: the first entry into implement, any return from writing code (an unlock approval, or a governing decision that makes the checkpoint stale), and the re-entry into implement after a breakdown-or-earlier reopen (operator, 2026-10-22, generalizing the original three events so built code is always inside the baseline). The baseline is a saved copy of every scoped test file, region-bearing file, and production file in scope, with fingerprints. Task relaunches, cancellations, and checkpoint rejections do not re-record it, so a relaunched or cancelled task cannot hide an earlier change. The checkpoint compares the current tree with the latest baseline. A production change outside every test task's declared files is refused at the checkpoint, except changes within the owned files of an implementation task that was running when the baseline was recorded and has since completed with verified changes. Declared changes are shown to the reviewer as diffs against the baseline copy.
   - The rule is language-agnostic. "Build and load" means compile, link, import, or collect as the language requires. Per-language notes in the test-authoring guide illustrate; they never define the rule.
   - The checkpoint reviewer reads and judges whether each test catches its named bugs, and writes plausible wrong implementations in a disposable workspace (the existing bounded investigation mechanism) wherever reading is not convincing. The operator will watch how well this judgment works.

4. **Red evidence is two checks, everywhere red is declared.**
   - Mechanically, a red check exits non-zero. A test task's check expectation may declare `nonzero` instead of an exact exit code, and task finish compares with that meaning; actual exit codes are recorded. A test task may declare exit 0 for a test that preserves behavior already built, judged at the checkpoint.
   - At the checkpoint, every declared whole-unit check runs, even after an earlier one fails, and the complete stdout and stderr are written to a named folder inside the unit's `.fbk/` folder. That folder is git-ignored, refused to the write hook, allowed as a review source both in the live tree and in a stored review snapshot, and excluded from the invisible-character scan (it is captured output, not an authored document). The files' fingerprints go into the checkpoint evidence, and they are required reading for the reviewer.
   - Declared whole-unit checks must report each test by name (for example a runner's verbose mode); the spec sets the commands.
   - The reviewer confirms from that output that each new or changed test failed on an assertion about missing behavior, and that every untouched scoped test either passed or is unchanged since the previous accepted checkpoint whose saved output shows it failing for the right reason. A build or load failure, a skipped test, or a test absent from the output is a blocker.
   - The exit-code-1 rule is retired from the red check, task expectations, the breakdown lock (while it lives), the reviewer obligations, and the guides.

5. **Test tasks own every test edit; the lock covers every scoped test.**
   - Test tasks write new tests, migrate existing tests whose expected behavior changes, and fix existing tests a signature change stops from building.
   - The spec names every path the unit creates. `scope.json` gains a `creates` list; a directory entry ends in `/`. Spec close checks that each declared path does not exist yet, fits the scope's sources, tests, or docs, and sits under a directory that exists or is itself declared. A declared directory fits the scope when it holds a scoped path. On a reopened spec, a declared path that exists because an earlier accepted spec of the same unit declared it is accepted; each spec close records its `creates` list for that check. The declared paths follow the design's module layout: extend existing files, modules, and functions where they fit, add new ones only where the design calls for a new responsibility, and never create a parallel file holding an existing file's responsibility. The spec guide states this, and the spec review checks every `creates` entry against the design and the existing code; a parallel file or one contradicting the layout is a blocker. (Operator, 2026-10-22: "The spec should name the files and directories to be created... They shouldn't be filling in information like this at implementation time.")
   - Plan validation judges each path a task lists by what it is: an existing path by its actual kind, a declared new path by its declared kind. A missing path the spec does not declare is refused, naming the path and saying the spec does not declare it. Plan validation rejects an implementation task that owns a scoped test. An owned file is checked against the test patterns as a file, so an implementation task owning `pkg/foo.go` beside the test pattern `pkg/**/*_test.go` is accepted. Owned directories and wildcard paths are checked for overlap with the test patterns, including files that do not exist yet. No kind is ever inferred from a path's name. A file with a declared test region (decision 6) may be owned by both a test task and an implementation task.
   - In writing code, the write hook refuses every scoped test path and every change to a test region, whether locked or new. A running implementation task's worker keeps writing within its ownership while an unlock is outstanding; no new implementation task starts.
   - The lock covers every scoped test file and test region.
   - At the checkpoint, tests that differ from the latest baseline must be red for the right reason or carry preservation evidence (decision 11); untouched scoped tests must pass or carry forward their red as decision 4 states.
   - A test task that finds an out-of-scope test broken reports a scope gap to the lead; it does not edit the file.

6. **Tests that share a file with code are supported as end-of-file regions.**
   - Test locations default to whole files matching the scope's test patterns. The scope may instead declare a test region for matching files: a start-line pattern, with the region running to the end of the file. That fits the convention of collecting in-file tests at the end, for example Rust's `#[cfg(test)] mod tests` or a C `#ifdef UNIT_TEST` block. Firebreak finds regions by text matching, never by parsing a language; per-language notes give example markers. A scope may declare regions without any whole-file test patterns.
   - A region is locked by its own fingerprint. The write hook computes the file as it would be after an edit and refuses a code-stage worker whose edit changes the region, or a test-stage worker whose edit changes the rest of a file it did not declare. If the after-edit file cannot be computed, the write is refused.
   - A region-bearing file appears whole in review snapshots, but only its region is immutable: the accepted-evidence write guard and the lock apply to the region, so production code above it stays editable after the checkpoint.
   - Tests interleaved with code throughout a file (for example Zig `test` blocks or D `unittest` blocks) are not supported by this amendment. The spec phase flags such a layout as unsupported, and the unit uses regions or separate test files.

7. **Locked tests are checked at every task boundary.** Task start and task finish compare every locked test file and region against its lock, including after task finish has run its checks, except files with an approved unlock outstanding. A mismatch refuses the finish and any new start, names the files, and records a lock-violation event naming the finishing task and every task running at the time. At lock time Firebreak saves a copy of each locked test file and region-bearing file in a named folder inside the unit's `.fbk/` folder; that folder is git-ignored and refused to the write hook as `state.json` is. A violation shows the diff, and one command restores the locked content: a whole locked file is replaced; a region is replaced while the current code above it is kept. The copies are deleted at implementation close. If implementation is reopened, the copies are saved again from the current files when those still match their locks. Shell commands are not pre-screened. For an existing project, the git-ignore entries are added to `.fbk/.gitignore` when missing.

8. **The traceability chain is enforced across phases, with coverage in both directions.** The operator raised this with the 0.6.0 author; it was dropped.
   - Each document has one named section holding its items: `prd.md` has **Commitments**, design files have **Design choices**, and `spec.md` has **Requirements**. Each item is a heading inside that section with a plain-language name. Everything else in the documents stays free-form. A design file without the section contributes no items and is not refused.
   - Links are ordinary Markdown links in the item's text, using the heading anchors Firebreak already resolves. A link counts only when it lands on an item in the correct upstream section. A renamed heading breaks its links loudly.
   - A design choice links to the commitments it serves. A requirement links to the design choices it comes from, or to commitments when the unit skips design. In a child unit, links to the parent unit's accepted items count.
   - Each task links to the requirements it serves; the link keeps its anchor, not just the file.
   - Design close: every design choice links to a commitment, and every commitment is covered by at least one design choice.
   - Spec close: every requirement links to a design choice, and every design choice is covered by at least one requirement. Without design, every requirement links to a commitment and every commitment is covered.
   - Breakdown close: every task links to a requirement, and every requirement is covered by at least one implementation task and, unless it is review-only (decision 9), at least one test task.
   - A commitment deliberately out of scope is removed or moved to an out-of-scope note during intent, not left uncovered.
   - At task launch, the task context carries each linked requirement's own section, its design choices' sections, and their commitments' sections. The 16,000-character task packet limit stays. *Amended by operator ruling, 2026-10-25: the chain and the rest of the packet each have their own 16,000-character limit, and breakdown close checks both for every task before launch does.* An oversize chain is refused with a message naming the task and the largest linked sections; the remedy is to split a task serving several requirements, or to tighten an oversized item section in its accepted document. An oversize rest is refused naming its largest fields; the remedy is to shorten the task's own fields or split the task.

9. **Whether tests are required is decided per requirement in the spec.**
   - A requirement is behavioral by default. A requirement no executable check can meaningfully verify (a convention, a documentation obligation) may carry the line `Checked by review: <reason>` under its heading. The spec review judges each marker and rejects it on observable behavior.
   - Breakdown derives test tasks from the requirements; it cannot opt a behavioral requirement out of testing. "Test" means any executable check matching the scope's test patterns or regions.
   - The implementation review returns an assessment for each review-only requirement, keyed by its anchor, through every review route, including the second reader's adjudication. Firebreak refuses a review result that omits one, and an assessment that the requirement is not met is a blocker.
   - Three outcomes, decided from reviewed inputs when writing tests ends (immediately on entering implement when there are no test tasks):
     - One or more test tasks: the normal flow.
     - No test tasks (allowed only when every requirement is review-only) and scoped tests exist: a preservation checkpoint. Every scoped test must pass, the reviewer judges whether they protect the code the unit will change, and they lock.
     - No test tasks and no scoped tests: no checkpoint and no lock; implement starts in writing code. The empty test inventory is recorded, and task boundaries and implementation close refuse any scoped test that appears later, including through the shell. Implementation close skips the checkpoint and lock requirements for that unit only.

10. **Breakdown close reviews the plan, not tests.** It reviews tasks, ownership, ordering, traceability, coverage, and each test task's named bugs. Plan validation (stage, references, verification, ownership, check expectations, ordering, and the task graph) stays at breakdown close, separated from test preparation. Breakdown no longer starts tasks, runs red checks, or locks. Entering or re-entering breakdown supersedes earlier task runs, as it does today.

11. **Reopening and wrong tests.**
    - Reopening breakdown or any earlier phase clears the locks, the saved copies, and the checkpoint's acceptance, and resets the checkpoint's generation and budget the way a later phase's are reset, with an event; the unit returns to writing tests. Reopening implement only keeps them.
    - At the re-run checkpoint, the operator's 2026-09-08 rule holds: tests unchanged since the previous accepted checkpoint keep its red evidence; new or changed tests for behavior not yet built need fresh red; changed tests that already pass because the code already does the right thing are accepted on reviewed preservation evidence; correct code is never undone to recreate red. The historical-red lookup moves from breakdown close to checkpoint acceptance.
    - A locked test found wrong during writing code is unlocked by name with the operator's approval and reason (`approve unlock-test`). The approval states, per named test, whether its corrected form is expected to fail (behavior not yet built) or pass (preservation). Approving the unlock clears the checkpoint's accepted evidence while keeping its rounds, budget and generation. While any unlock is outstanding the unit is in writing tests.
    - A test task reworks the named tests. Firebreak sees only command exit codes, so the approval's expectations apply per command. The unlock request the operator approves carries the rework commands: each an argument array scoped to some of the named tests, with its expected outcome (zero when all its tests are expected to pass, non-zero otherwise). The rework task's run uses those commands and expectations in place of the ones declared in `tasks.json`, which stays unchanged, so breakdown's acceptance is untouched. Per-test judgment stays with the checkpoint reviewer reading the saved output. The checkpoint then runs again, spending a round from its own budget, and locks on pass.
    - `lock-tests` and `check-tests` are removed. The checkpoint is the only way to lock.

12. **In-flight units are not migrated.** The Realmind unit finishes on installed 0.6.0; the operator refactors it afterward with the amended Firebreak. The state format's version number increases in the step that first changes the record's shape. The new code refuses an older record with a message naming this amendment and the remedy: move the unit under `.fbk/archive/`, which Firebreak skips. Realmind is not reinstalled until that unit closes.

## Review and build process

- **Plan review ends with one targeted round.** After three full rounds, a final round by both reviewers reports only blockers and contradictions between decisions. Code-fitting findings from that round and earlier rounds are collected but do not block. The targeted round found one blocker and two contradictions; after the fixes, a confirmation round came back clean from both reviewers on 2026-10-22. Every round's output is in `evidence/test-stage-amendment-reviews/`.
- **Code-fitting findings go into the build briefs.** Each step's subagent receives the review findings that apply to its step as a checklist it must address or explain.
- **Each commit is reviewed until clean, with a cap.** After each step and before committing, a reviewer checks the actual diff against this plan and that step's findings; rounds repeat until one comes back with no blocker or major finding. Blockers always stop a commit. Once a step has had three rounds past its first round with no blocker, it commits at the reviewed state and any remaining majors go to the follow-up list below, pinned as strict expected-failure tests where tests exist (operator, 2026-10-22).

## Follow-ups

Majors left open by the review cap, each pinned by a strict expected-failure test that fails loudly once fixed.

- **A standalone review round misses a link retarget after capture** (follow-up group B). After a standalone round captures a link's target, retargeting it between equal-content files leaves the round reporting its snapshot current and intact, so contributors resume against the old link listing and the result stays eligible for remediation. Fix: compare live link targets with the captured map when checking standalone drift, and bind that map into the standalone contract.
- **A list item with extra spaces after its marker hides a later section** (follow-up group C). Before a traceability section, a list item written `-  Example` is not tracked as a list, so a fence inside it is read as running to the end of the file and the section it hides goes unchecked, although Markdown ends that fence with the list item. Fix: track list indentation outside the sections independently of the plain-shapes check.
- **A nested numbered item not starting at 1 hides an indented link** (follow-up group C). Under a list item, `10. Restore backups` directly after the item's text continues that text in Markdown, so a link indented below it renders as code yet counts. Fix: track paragraph state at each list depth and refuse a nested numbered list not starting at 1 without a blank line before it.
- **A reference definition with a wrapped label escapes the definition check** (follow-up group C). A definition whose label spans two lines is not recognized, so bracketed text in an item can silently resolve through it. Fix: recognize definitions with wrapped labels outside fenced code and refuse them.
- **Each commit gets an intent check.** Before committing, a fresh agent compares the change with the operator's stated intent and this plan, and lists anything missing, anything built that nothing asked for, and any divergence. A review finding that would widen scope goes to the operator before it is built (operator, 2026-10-22).
- **The build starts only on the operator's word.** Settling this plan does not start it.

## Build order

Each step is one commit on `develop/0.6.0-astra`, built by subagents and checked by the lead. Each step's tests are written first and observed failing. Before each commit, the full local suite runs: pytest, the installer suite, and the workflow shell suites. Every commit leaves the workflow usable end to end. Guides, skills, the architecture overview, the glossary, and the decisions log change in the same step as the behavior they describe. The untracked `.fbk/` folder stays out of every commit.

1. **Stages inside implement (additive).** Implement derives its stage, and task start reads it: a test task is refused in writing code and an implementation task outside it. Entering implement no longer requires locks. The write hook applies the stage: in writing tests, a test task's worker may write its declared test and production files; in writing code, no worker may write any scoped test path, and running implementation workers keep their ownership during an unlock. The spec's `creates` list in `scope.json`, its spec-close checks, the spec guide paragraph on following the design's module layout, and the spec review obligation for `creates` entries. Plan validation judges listed paths by actual or declared kind, refuses undeclared missing paths, rejects implementation tasks that own a scoped test (files checked as files, directories and wildcards by overlap) and accepts declared production files on test tasks; that allowance is usable only in implement until step 4. Breakdown still prepares and locks tests exactly as today, so a lock from breakdown derives writing code. The shared lifecycle fixture drops `tests/check.py` from its implementation task. Continuation stops reporting unrun test tasks as completed.

## Done means

Each item is proven by a test unless it says otherwise.

- **Flow.** A unit runs intent through implementation where breakdown writes only tasks, test waves run in implement, the checkpoint review locks the tests, and implementation waves follow. Implement can be entered with no locks.
- **Refused orderings.** An implementation task before the lock; a test task after it; an implementation task owning a scoped test, including by wildcard or folder; an implementation worker writing a new scoped test file or changing a test region; any route to locking without the checkpoint; implementation close without a current accepted checkpoint (outside the no-tests outcome); a task with no requirement link; a behavioral requirement with no test task; any requirement with no implementation task; a design choice or commitment left uncovered.
- **Declared paths.** Spec close refuses a `creates` entry that already exists, falls outside the scope, or sits under an undeclared missing directory; plan validation refuses a task listing a missing path the spec does not declare; a declared new directory with a dot in its name (`pkg/v1.2/`) is judged as a directory and a declared new extensionless file (`Makefile`) as a file.
- **Accepted ownership.** An implementation task owning `pkg/foo.go` beside the test pattern `pkg/**/*_test.go` is accepted; a region-bearing file owned by a test task and an implementation task is accepted.
- **Stage derivation.** A never-started test task keeps the unit in writing tests; a rejected checkpoint followed by a relaunched test task returns it to writing tests; an outstanding unlock does the same.
- **Baseline.** A test task that writes a red test and is relaunched (or cancelled and relaunched, or relaunched after a rejected checkpoint) without changing it still has that test counted as changed, because none of those events re-records the baseline; an undeclared production change is refused at the checkpoint; the reviewer sees declared production changes as diffs against the baseline copy, including when the source was already modified before writing tests began.
- **Red.** A Go-shaped fixture where a changed signature breaks callers and a Python fixture both reach a meaningful red through the production-change allowance; a test expectation with exit code 101 completes; every declared check runs after an earlier one fails; the reviewer's actual snapshot contains the complete saved output when it exceeds the old 12,000-character and 1 MiB limits, with decisive evidence near the start; output containing terminal color codes passes the hygiene scan; a checkpoint where a changed test unexpectedly passes without preservation evidence, or an untouched test fails without carried-forward red, is not accepted. The reviewer instructions name build or load failures, skipped tests, and tests missing from the output as blockers (verified in one isolated checkpoint exercise, not a unit test).
- **Checkpoint.** Its budget is independent of implement's; an interrupted checkpoint recovers; budget extension, approval over findings, and dispositions of its test-remedy suggestions work; a pass demands no phase observation; writing code does not make an accepted checkpoint stale; the implement review's comparison baseline is the accepted checkpoint snapshot, including its saved output; status and continuation report it correctly before tests run, after rejection, after exhaustion, and after resume.
- **Locks.** A locked test changed through the shell is caught at the next task start and at task finish, including a change made while finish runs its checks; the event names the files and running tasks; restore reproduces the locked content exactly; copies are deleted at implementation close; implement reopen re-saves copies when files match and refuses when they do not; an existing project's `.fbk/.gitignore` gains the new entries.
- **Unlock rework.** Unlock approval clears the checkpoint's acceptance and re-records the baseline; the rework test task finishes despite its test differing from the lock; with two named tests, one expected to pass and one to fail, the approval's scoped commands replace the task's declared ones and complete against their expectations without changing `tasks.json`; an implementation task running at the approval finishes its owned-file changes and the re-run checkpoint accepts them; a corrected test expected to pass against already-correct code reaches checkpoint acceptance without undoing that code; other locked tests for unbuilt behavior stay red with their carried-forward evidence; the checkpoint re-locks.
- **Reopen.** Reopening spec or breakdown after code exists clears locks, resets the checkpoint's generation and budget, and returns to writing tests; unchanged tests carry their earlier red; reopening implement only keeps locks.
- **Regions.** A Rust-shaped file with a `#[cfg(test)]` region: after an accepted checkpoint, an implementation edit above the region is allowed and one inside it is refused; a shell change inside it is caught at the next boundary; restore replaces the region and keeps a valid production edit above it; a regions-only scope is accepted.
