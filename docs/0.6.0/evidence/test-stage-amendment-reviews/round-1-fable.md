## Independent findings

### I-1 — blocker — Build order, step 1: one commit removes a mechanism wired through nine modules and fifteen test files (overlaps Astra 1, 3)

Breakdown-time test preparation is not one module. Removing it touches: `test_preparation.py` (whole file, 371 lines); `engine.py:222-238` (`begin` on breakdown enter and resume), `engine.py:412-415` (status calls `progress`); `close.py:37-42, 116, 143, 272-288`; `handoff.py:272-274, 331, 647-651`; `review.py:665-685, 1042-1064`; `review_baseline.py:35-41`; `cli.py:373-434, 554-579` (`check-tests`); `hooks.py:161-169`. On the test side, the shared fixture pattern drives every unit through breakdown via `test_preparation.capture` (`test_workflow_lifecycle.py:138-148`, `accept()`), and that pattern is copied into at least 15 files (grep for `test_preparation|check-tests|lock_tests` hits `test_workflow_test_preparation.py` 24 times, `test_workflow_lifecycle.py` 10, `test_workflow_decisions_dispositions.py` 10, `test_preparation_lineage.py` 8, plus 11 more files). The lifecycle fixture itself violates decision 5: its implementation task owns `tests/check.py` (`test_workflow_lifecycle.py:92-98`), so step 1's validator will reject it and every file sharing it must change in the same commit. Step 1 also bundles four new behaviors (stage derivation, stage-gated task start, stage-aware hook, validator). That is the overscoping shape the plan warns against.

Smallest fix: split step 1 and reorder so the workflow is never broken. 1a: derive the stage and gate task start and the write hook by stage inside implement, while breakdown preparation stays allowed (a lock from breakdown simply derives "writing code"; existing tests keep passing). Then step 2 (checkpoint; the lock can come from either path). Then 1b: remove breakdown preparation, `check-tests`, `lock-tests`, and the breakdown lock, and rewrite the fixtures. Then steps 3 and 4.

### I-2 — blocker — Build order, step 1: entering implement is refused once breakdown stops locking

`engine.enter` calls `verify_locks` before consuming the start-implementation grant (`engine.py:232-234`), and `verify_locks` raises when `record["locks"]` is empty (`engine.py:357-361`). After step 1 as written, `phase-enter implement` fails for every unit, so no test task can ever run. Step 1 lists task start, the hook, the validator, and breakdown close, but not phase entry. The same gap sits in the hook: during implement, any non-test write is denied until locks exist (`hooks.py:170-172`, "Write, exercise, and lock the behavior tests before implementing source"); step 1 does name the hook, so that one is covered, but the entry check is not.

Smallest fix: name `engine.enter` in step 1 (drop `verify_locks` at entry; the lock requirement moves to implementation close, which already has it at `close.py:44`). Add to "Done means": implement can be entered with no locks.

### I-3 — major — Decision 1 vs. `reopen`: locks survive a breakdown reopen, so the derived stage is wrong on re-entry

`engine.reopen` clears later-phase evidence and bumps generations but never touches `record["locks"]` (`engine.py:264-281`); `test_reopen_supersedes_later_open_phase_and_preserves_locks` (`test_workflow_lifecycle.py:318`) pins that, and `docs/architecture-overview.md:25` documents it ("Reopening ... retains test locks"). Under decision 1, "tests locked" means "writing code". So: reopen breakdown to add or change a test task, re-enter implement, stage derives "writing code", the new test task is refused by step 1's rule, and the checkpoint cannot run. `lock_tests` also refuses a re-lock when a locked file changed without an unlock (`engine.py:338-342`). Step 3's "re-saving on reopen" only covers reopening implement.

Smallest fix: in step 1, reopening breakdown or any earlier phase clears `locks`, `unlocks`, and (after step 3) the saved copies, with an event; reopening implement keeps them (as decision 6 says). Update the lifecycle test and the architecture overview line in the same step.

### I-4 — major — Build order, step 2: "reuse of the phase review machinery" is keyed by phase name into `record["phases"]`; a record "beside the phase records" has no way in

Every function the plan wants to reuse locates its work by `record["phases"][phase]`: `close._close_phase` (`close.py:107, 171, 196`), the budget-exhaustion handler (`close.py:79-89`), `review.review` (`review.py:709`), council progress (`review.py:808`), `status_report`'s `human_review` block, which is computed for the current phase only (`engine.py:396-410`) and feeds the Stop hook (`hooks.py:336-338`), `focus_brief` (`review.py:900-906, 994`: `names[phase]` and `objectives[phase]` raise `KeyError` for anything that is not a phase), `decisions.for_readers` (silently falls back to the last phase, `decisions.py:278`), and `grant_target` for close-over-findings (`engine.py:139`). The CLI restricts `phase` for `phase-close`, `recover-close`, `extend-review`, and `approve --phase` to `evidence.PHASES` (`cli.py:36-37, 159`), so the escalations decision 2 says happen "as they do at phase close" (extend-review, recover-close, close-over-findings) cannot address the checkpoint at all. Step 2 says "reuse" without saying how the record is addressed.

Smallest fix: decide in step 2 that the checkpoint record lives at `record["phases"]["test-checkpoint"]` (same shape as a phase entry) and list the sites that must accept that key: the CLI choices above, `focus_brief` (a sixth objectives entry), `for_readers` (treat as implement), `status_report` (surface its exhaustion when the open phase is implement), and `review.review`'s detection guidance branch (`review.py:663-666`). Loops over `record["phases"].items()` (`engine.py:458-471`) and over `ev.phases(record)` (`engine.py:53`) tolerate the extra key already.

### I-5 — major — Decision 2 / step 2: the checkpoint's "review-plan choice" has no mechanism for implement-like reviews

`review_plan.PHASES = ("design", "spec")` (`review_plan.py:7`); `require` returns `None` for any other phase (`review_plan.py:109-111`); `defaults` rejects other keys in config (`review_plan.py:42-43`); the CLI limits `--phase` to those two (`cli.py:63`); `implementation.md:24` states breakdown and implement use the fixed headless reviewer with an optional second reader. So the checkpoint record's "review-plan choice" is either always `None` (then the words in decision 2 and step 2 describe nothing) or review-plan has to be extended to a new phase name, which is scope the plan does not budget.

Smallest fix: in step 2, state that the checkpoint uses the same fixed reviewer as breakdown and implement (single native reader plus optional configured second reader) and drop "review-plan choice" from the record's field list; keep rounds, round budget, generation, and accepted evidence.

### I-6 — major — Decision 4: retiring the exit-code-1 rule stops at the red check; task-level expectations stay pytest-shaped

`test_preparation.plan` restricts every `check_expectations.exit_code` to `{0, 1}` and `1` to test tasks (`test_preparation.py:206-225`); `finish_task` marks a task needs-attention unless each exit code equals the declared one (`handoff.py:905-913`); the reviewer obligations say "Expected red (exit 1)" (`review.py:971`), as do `breakdown.md:39` and `handoffs.md:44`. Decision 3 makes the test task's own checks the first place red is observed. `cargo test` exits 101 on failing tests; `ctest` exits 8; `go test` exits 1 for both a build failure and a test failure. A Rust test task cannot declare a passing expectation under the current validator. The "Done means" Go fixture will not catch this because Go happens to exit 1.

Smallest fix: in the same step as decision 4, let a test task's expectation be "nonzero" (accept the literal string or any integer other than 0 for stage tests), compare with that meaning in `finish_task`, and regenerate the reviewer sentence from the same source. Add a Rust-shaped expectation (exit 101) to the done-means list or a unit test.

### I-7 — major — Decision 4 / step 2: "Firebreak saves its full output" has no home, and the reviewer cannot read it where the plan puts it

`run_command` keeps at most the last 1 MiB of each stream (`review.py:244-248`); `verify` and `check-tests` trim to the last 12,000 characters (`review.py:310-313`, `cli.py:427`); `bounded_checks` bounds what enters the prompt (`review.py:833`, used at `1036-1050`). The reviewer runs against a snapshot of the `required` set (`review.py:673-693`) and is told not to read `state.json` or review logs (`review.py:1107-1108`). Storing the full output in a state event, as `tests-locked` does today (`engine.py:345-352`), bloats a record that is hashed on every load and save (`store.py:122, 138`). Decision 5's "untouched existing tests must still pass" is only checkable by reading which tests failed in that output, so truncation also silently weakens that rule.

Smallest fix: step 2 writes the red run's stdout and stderr to files under the unit's `.fbk/` folder, records their hashes in the checkpoint evidence, and adds those paths to the checkpoint review's `required` set so they land in the snapshot; add "the reviewer's snapshot contains the full red output" to done-means.

### I-8 — major — Decision 7 / step 4: "requirement" is not identifiable, so the breakdown coverage check cannot be written

Decision 7 says each requirement, design item, and intent item is its own heading, and breakdown close checks "every requirement is covered". `spec.md` also carries headings that are not requirements (the spec guide asks for conventions, scope, verification, threat analysis: `spec.md:5-32`); `prd.md` has problem, scope, open decisions (`intent.md:1`). The anchor resolver resolves any heading (`handoff.py:466-477`). Nothing in the plan says how Firebreak tells a requirement heading from a section heading, how a design item in `design/` (a directory of files, `evidence.py:169`) is enumerated, or what link syntax inside prose Firebreak parses (task refs use `path#slug`; `repair._reference` already parses Markdown links `[label](target#fragment)`, `repair.py:68`). Also unaddressed: whether a child unit's requirement may link to a parent spec item (`handoff.py:675-676` already treats the parent spec as authoritative).

Smallest fix: in step 4, fix the convention (for example: items are the headings nested under a named parent heading per document, "Requirements", "Design items", "Intent items"; links are Markdown links with the resolver's slug), say parent-spec items are valid link targets or not, and put the convention in the three guides and the glossary in the same step.

### I-9 — minor — Decision 7: chain text in the task packet vs. the 16,000-character packet cap

`task_packet` refuses launch above 16,000 characters (`handoff.py:601-604`), and the packet already carries two guides (`handoff.py:597-600`). Carrying the text of each linked requirement, its design items, and their intent items for a task that serves several requirements will exceed that cap and refuse launch with no narrowing possible (the refs are mandatory). Smallest fix: state in step 4 that the chain carries each item's own heading section only, lists any omitted items by anchor, and counts against the cap, or raise the cap deliberately.

### I-10 — major — Decisions 1, 2, 5, 6: the unlock-test crossing and the re-lock path are left undefined

`approve unlock-test` exists (`engine.py:161-162, 175-177`); `verify_locks` refuses close while `unlocks` is non-empty (`engine.py:358-361`); re-locking goes through `lock-tests`, which enforces the exit-code-1 rule decision 4 retires (`cli.py:573-579`, `engine.py:325-328`); `implementation.md:16-22` documents the whole path. Decision 1's three stages do not cover "locked, with pending unlocks"; decision 5 says test tasks own every test edit, but today's unlock lets the lead edit the named test; decision 2 says rework happens through test tasks. The plan neither retires the crossing nor defines its stage.

Smallest fix: pick one in step 2. The one consistent with decisions 2, 5, and 6: retire `unlock-test` and `lock-tests`; a wrong locked test is fixed by a scoped reopen that clears the named files from `locks` (stage reverts to writing tests), a test task reworks them, and the checkpoint runs again. Say so and update `implementation.md`.

### I-11 — major — Build order, step 1: continuation reports every test task as completed as soon as breakdown is accepted

`handoff.continuation` defaults a test task's status to `"completed"` when breakdown has accepted evidence and the task has no run (`handoff.py:331`). Once test tasks run in implement, the implement lead's first `continuation` will list every test task as done before any ran. Step 1 does not name it. Smallest fix: drop the default in step 1 and add to done-means: after breakdown close, continuation lists test tasks as unassigned.

### I-12 — minor — Build order, step 1: `begin()`'s side effects need a named replacement

`test_preparation.begin` resets `task_runs` with a `task-assignments-superseded` event on every breakdown entry (`test_preparation.py:87-95`) and seeds the baseline that `plan()` uses to refuse a stub over an existing source (`test_preparation.py:192-197`). If step 1 deletes it: stale completed runs survive a breakdown reopen and surface as blockers only at implementation close (`handoff.py:975-994`); and the `stubs` field loses its meaning, since decision 3 lets a test task declare existing production files. Smallest fix: in step 1, move the run reset to `engine.reopen`/breakdown entry, and state that `stubs` is retired in favour of the task's declared `files` (test patterns and declared production files), with `plan()` checking only that each is in scope.

### I-13 — minor — Decision 6: saved copies in the unit's `.fbk/` folder are committed to git and writable through the hook

Only `.fbk/runtime/` is ignored (`cli.py:195`); copies under `.fbk/<unit>/` enter any commit made during implementation. The write hook allows any path under the unit directory for the owning session (`hooks.py:101-104, 143-144`), so a worker or lead can edit a copy with `Edit`, defeating the restore command. Smallest fix: step 3 names the copies directory, adds it to `.fbk/.gitignore`, and has the hook refuse it the way it refuses `state.json` (`hooks.py:92-99`).

### I-14 — minor — Decision 8 side effect: the implement review loses its test baseline

`review_baseline.select` falls back to breakdown's accepted snapshot as the "accepted test contract before first implementation" (`review_baseline.py:25-28`); that snapshot contains tests only because the breakdown review adds them to `required` (`review.py:678-685`), which decision 8 removes. Smallest fix: in step 2, make the checkpoint's accepted snapshot the implement review's fallback baseline (one branch in `select`).

### I-15 — minor — Decision 9: the state format changes but `schema_version` stays 1

`store.load` accepts only `schema_version == 1` (`store.py:118`). An old record (no checkpoint entry, breakdown-era `test_preparation`) loads silently and then hits `KeyError`-shaped failures in the new code. Smallest fix: bump to 2 in step 2 and refuse older records with a message naming the amendment; the plan already accepts that in-flight units are not migrated.

### I-16 — minor, raised to major after pass 2 (see ruling 2: `lock-tests --preserve-existing` locks without running any check) — Build order, step 2: `lock-tests` remains a second way to produce locks, so "implementation close without a passed checkpoint" is not refused

`lock-tests` stays in `COMMANDS` (`__init__.py:12`) and in implement (`cli.py:390, 573-579`); implementation close requires locks (`close.py:44`), not a passed checkpoint. The done-means test for this ordering passes only if the command is removed or close checks the checkpoint record. Smallest fix: step 2 removes `lock-tests` and `check-tests` from `COMMANDS` and the CLI, and `close._ready` for implement checks the checkpoint's accepted evidence.

### I-17 — major — Decision 2: test-remedy suggestions raised by the checkpoint review cannot be dispositioned, so the checkpoint can never pass when it raises one

Today breakdown close blocks the lock until the review's own test-remedy suggestions are dispositioned (`close.py:272-287`). Dispositions are validated against `suggestion_dispositions` (accepted phase reviews) plus `round_suggestions`, which reads only `record["phases"][open_phase]`'s latest round (`handoff.py:79-93`; `decisions.py:90`). A checkpoint round's suggestions are invisible to `decision-record`, so the operator cannot record a disposition and the checkpoint blocks forever. Smallest fix: in step 2, `round_suggestions` also reads the checkpoint record when the open phase is implement (trivial if I-4's pseudo-phase placement is taken).

## Rulings on the Astra review

1. **Confirmed; proposed fix is larger than needed and runs against the one-step-at-a-time constraint.** `engine.py:232-234` requires locks at implement entry; `close.py:287` is today's only producer; `test_workflow_lifecycle.py:138-148` prepares and locks in breakdown and is the shared fixture. Astra's fix (phase move + minimal checkpoint + fixture rewrite in one commit) recreates the overscope. The additive ordering in I-1 (stage gates first while breakdown locking still works, checkpoint second, removal third) keeps every intermediate commit green with a working route into writing code.

2. **Confirmed.** `cli.py:554-579` calls `engine.lock_tests` directly; `engine.lock_tests` (`engine.py:313-354`) needs no review; and with `--preserve-existing` the `checking` flag at `cli.py:373` is false, so no check runs before the lock. Under "locked means writing code" this is a checkpoint bypass. I had it as minor (I-16); Astra's blocker rating is fair against the done-means sentence "each forbidden ordering is refused by the state machine". Fix (remove the command or route it through the checkpoint) is the right size.

3. **Confirmed.** `close.py:37-42` reaches `test_preparation.ready` → `validate_sources` → `plan` (`test_preparation.py:314-315, 243-244`), and `plan` (`144-240`) is where stage, acceptance-ref, verification, stub, expectation, test-before-implementation, and `task_graph.validate` checks live. `review.py:678-685` adds tests and stubs to the breakdown snapshot and `review.py:967-978` tells the reviewer to inspect tests and red output. Step 1 must keep `plan` and rewrite the breakdown review inputs and obligations; the plan does not say so. Fix is right-sized.

4. **First half confirmed, second half overstated.** `task_run_blockers` (`handoff.py:963-968`) only demands assignment of implementation tasks; a stage predicate built on existing runs would let a never-started test task vanish from readiness, so the predicate must walk `tasks.json`. The "contrary to blockers keep the stage at writing tests" part does not hold as a mechanism conflict: relaunching a completed task is already allowed (only a running assignment is refused, `handoff.py:653-656`), so after a blocking checkpoint the lead relaunches the test task, it is running, and the stage derives "writing tests". The plan's wording is loose, not wrong; it should say "ready for checkpoint" still permits test-task launch. Fix is slightly larger than needed ("which recorded rejection facts return the unit to writing tests" needs no new fact).

5. **Confirmed; fix is larger than needed.** Pending guards iterate `record["phases"].values()` (`hooks.py:133`, `handoff.py:625`); recovery indexes `record["phases"][phase]` (`close.py:374-392`); review choices are design/spec only (`review_plan.py:7`); `suggestion_dispositions` iterates `evidence.phases(record)` (`handoff.py:66-76`) and `round_suggestions` reads only the open phase (`handoff.py:79-93`). All true, and the dispositions gap is the sharp one (I-17). But "adapt ... without turning it into another phase" is the expensive path: storing the checkpoint under `record["phases"]["test-checkpoint"]` (not in `evidence.PHASES`, so not a phase) makes the pending guards, recovery, extension, and retrospective sections work unchanged; only the CLI choices, `focus_brief`, `for_readers`, `status_report`, and the two suggestion readers need a line each (I-4). The review-plan point is better resolved by dropping the "review-plan choice" words (I-5) than by extending selection.

6. **Confirmed.** `test_preparation.py:192-197` refuses a stub over a baseline source, `198-204` limits test-task ownership to tests plus stubs, and `validate_sources` (`243-259`) refuses any baseline change. Hook permission alone does not deliver decision 3. The fix's last clause ("supply before/after source evidence") is already largely present: `start_task` records `before` hashes (`handoff.py:733`) and `finish_task` records after-hashes (`handoff.py:892-896`), so the checkpoint needs only to expose them.
