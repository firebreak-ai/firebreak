# Firebreak 0.6.0 implementation plan

Branch: `develop/0.6.0-astra`. Baseline: `e889a0b` (includes the operator's existing documentation edits). Written 2026-09-06.

## Objective

Produce maintainable code aligned with the human's intent by making the accepted behavior, current evidence, and next action explicit. Use deterministic code for bookkeeping and policy; use model judgment for design, implementation, and review. An increasing number of reviews or documents is not success.

The operator authorized an evidence-informed plan and implementation in an isolated branch, with authenticated Claude Code subscription runs inside this container. Existing approved design decisions are inputs to reconsider when necessary to preserve this objective. Changes from the prior design are recorded below rather than silently presented as its implementation.

No available evidence proves that more ceremony produces more maintainable code. The defaults below are engineering choices to test, not conclusions claimed by the research.

## Design decisions

1. **One transaction per unit.** Store unit configuration, open-phase facts, acceptance evidence, grants, test locks, review history, and audit events in one versioned JSON document under `.fbk/<unit>/state.json`. Update under a file lock with atomic replacement. Phase is derived from these facts and the current artifact digests; there is no agent-maintained status field. This replaces the proposed multi-file commit/recovery protocol. Human-readable status is generated by `fbk.py status`.
2. **Evidence has a revision.** A phase close records the complete subject file set and content digests, prerequisite evidence, verification results, and review result. Changed or missing inputs invalidate acceptance automatically. Record checksums detect accidental record damage, not malicious modification. Unit paths and artifact paths remain confined to the repository.
3. **Explicit ownership.** A session may own one phase. A unit permits one owner session; another session must explicitly take over with a recorded reason. Workers are registered under the owner, and known active workers prevent closing. Interrupted work can be resumed from disk.
4. **One phase API.** `phase-enter`, `phase-close`, `approve`, `route`, `lock-tests`, `status`, and `workflow-report` are the primary operations. Hooks and explicit commands use the same functions. Direct command expansion and agent Skill calls both enter phases. Explicit phase entry is an idempotent fallback, so host-specific entry gaps cannot silently skip prerequisite validation at close.
5. **Bounded review.** Reviews inspect revision-bound artifacts and report demonstrated defects separately from suggestions. The phase's round budget survives fixes, retries, and restarts. Reaching it stops automated review and exposes unresolved findings; continuing requires an explicit budget extension or a scoped acceptance grant. Independent review is the default; an optional second configured reader adds diversity without being required for every small task.
6. **Human approval is scoped.** Grants name the crossing and current revision. Implementation entry, reopening accepted work, unlocking tests, and accepting unresolved findings are recorded. Agent-supplied words are an audit record, not cryptographic proof of consent. Commands do not infer consent from a permission mode or previous unrelated approval.
7. **Test integrity is behavioral.** Explicit repository-relative test paths replace filename guessing as lock authority. Tests must fail for the intended missing behavior, then pass after implementation. Test review asks whether a realistic wrong implementation would fail. Implementation close runs declared verification commands and validates locked tests. No requirement to predeclare private function signatures.
8. **Small hooks.** The policy adapter checks entry, covered writes, and bounded turn completion. Source edits outside the declared implementation scope are rejected while work is active. Bash and external edits remain a documented prevention gap; content revalidation at close is the backstop. Ordinary work outside an opted-in workflow remains unaffected. Recording failures do not block work.
9. **Durable intent, disposable execution detail.** Keep requirements, design, spec, and accepted evidence in git. Keep runtime locks and telemetry untracked; durable ownership and worker attribution stay in the unit record. Retain the single state document on completion; avoid archive restoration as a prerequisite for reopening. Superseded workflows remain in git history.
10. **Progressive skills.** Phase skills route `.fbk` units to the current workflow. The new instructions carry objectives, relevant inputs, and measurable acceptance criteria. Standalone review remains available. Shared guidance is referenced through a consistent installed-path convention.

## Implementation sequence

- Establish baseline and verify actual hook payloads with a scratch project.
- Implement and behaviorally test transactional storage, path confinement, evidence freshness, hierarchy, grants, ownership, reopening, and routing.
- Add structural validation, explicit verification commands, test locks, persisted review budgets, and a read-only headless review runner.
- Wire hooks and skills to the same API; add recovery/status and nonblocking telemetry.
- Exercise installation in temporary directories, complete end-to-end lifecycle tests, and run selected mutations to show the tests detect broken invariants.
- Run the full regression suites in their expected working directories, independently review the implementation, resolve defects, and commit a reviewable result with limitations and reproduction commands.

## Acceptance scenarios

- A direct `/fbk-spec` and an agent-invoked Skill cannot enter spec before prerequisites pass.
- Modifying an accepted spec invalidates downstream readiness, including after process restart.
- Failed verification, incomplete/invalid review output, and a missing locked test cannot close implementation.
- Concurrent record updates retain both changes; interruption before replace preserves the old valid document.
- An approval for one revision or crossing cannot authorize another; unlock scope covers only named tests.
- A child cannot accept work against an unaccepted or changed parent spec without acknowledging the current parent.
- A resumed phase retains review rounds; fixes cannot reset the budget. Advice alone cannot force an endless repair cycle.
- A second session cannot silently replace the owner; explicit takeover restores the same durable work.
- Hooks emit the documented decision shapes, guard Stop recursion, and remain silent in unconfigured projects.
- Installation, upgrade, and uninstall preserve unrelated settings. Legacy commands continue to function during migration.

## Evaluation

Tests that assert prose, counts of sections, or implementation structure are classified as asset checks, not evidence of runtime correctness. The new runtime tests use observable results and injected failures. A small mutation audit must demonstrate detection of stale evidence, skipped prerequisites, omitted test-lock verification, and incorrect grant scope. A later real-project comparison should measure missed requirements, regressions, human interventions, unnecessary changes, and the cost of a follow-up change using the actual target model; this implementation cannot establish longitudinal maintainability overnight.
