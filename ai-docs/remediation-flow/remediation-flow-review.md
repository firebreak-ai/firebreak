# Remediation Flow — Stage 2 Review

## Review summary

Four council perspectives reviewed the project-level overview spec independently. Total findings: **42** (9 blocking, 26 important, 7 informational).

**Cross-agent convergence** — three themes hit by multiple perspectives independently:
1. **Defense-in-depth taxonomy is inflated.** Builder (F-B1) says only three of six named layers are real defenses; Security (F-SEC-02, F-SEC-03, F-SEC-04) says the Semantic layer is contaminated, the Functional layer is correctness-not-contamination, and the Post-hoc layer is detection-not-prevention. Independent agreement that the six-layer claim is rhetorical rather than structural.
2. **Council ceremony is heavier than it earns.** Builder (F-B2) says triple-council deliberation (intent + rearchitecture + spec review) won't survive a real cycle; Security (F-SEC-02) adds that council members above the firebreak are themselves contaminated, undermining their defense value.
3. **Hypothesis-gating discipline is uneven.** Builder (F-B10, blocking) calls out that the spec commits "no investment beyond Feature 1" while simultaneously bootstrapping repo-wide glossary infrastructure, three-council ceremony, and a six-layer defense taxonomy. The decisions resolved during scoping pre-judge Features 2–8 in ways the parent doesn't acknowledge as revisitable.

**Net read across perspectives**: the spec is structurally sound at the high level — vision, architecture, feature decomposition, and hypothesis-gating intent all coherent. The findings cluster around (a) seam-and-naming issues from this session's restructuring (wave terminology collision, "caller-update wave" residue, path-convention gaps for reused skills), (b) ceremony that doesn't earn its place under the hypothesis-gating commitment, (c) measurement methodology gaps in the load-bearing Feature 1 gate framing and Feature 8 numeric criteria, and (d) threat-model gaps in the firebreak's coverage claims (escape paths, `Bash` tool, "with care" reads above the firebreak).

The blocking findings split into two cohorts: must-fix-before-child-specs-start (architectural — A1, A2; security — F-SEC-01, F-SEC-02, F-SEC-05, F-SEC-06) and must-fix-for-the-validation-experiment-to-be-interpretable (analyst — F1, F2; builder — F-B10).

## Findings

### Architectural soundness

#### A1 — "Wave" terminology collides between Firebreak's per-wave verification and the rearchitecture's foundation-first wave order
**Severity**: blocking
**Description**: The parent spec uses "wave" in two distinct senses. Cycle-scope wave: `wave-order.yaml` is a topological sort of the *module* dependency graph; the per-module loop body runs once per module in foundation-first wave order. Feature-scope wave: inside `/fbk-implement` (verified at `assets/fbk-docs/fbk-sdl-workflow/implementation-guide.md`), "wave" denotes a *task-batch* with per-wave verification, baseline-snapshot regression, and a wave checkpoint. `task.json`'s `wave_id` field uses this meaning. Each per-module spec → breakdown → implement run will produce its own internal `wave_id` stream executing inside the rearchitecture's outer "wave order." Child specs for Features 3, 6, 7 will all need to reason about both senses simultaneously. **Resolution**: rename one of them in the parent spec before child specs inherit. Suggested: keep "wave" inside `/fbk-implement` (well-established) and introduce a different term for the per-module ordering — candidates: "module sequence," "cohort," "stratum." Update `wave-order.yaml` filename, the integration-seam bullet, and all parent-spec prose accordingly. Add a glossary entry per the project's own terminology-hygiene discipline.

#### A2 — Reused skills reference `ai-docs/<feature>/` paths and `$HOME/.claude/fbk-scripts/fbk.py`, but the worktree's sparse-checkout will exclude both
**Severity**: blocking
**Description**: The "REUSED" skills (`/fbk-spec`, `/fbk-spec-review`, `/fbk-breakdown`, `/fbk-implement`, `/fbk-code-review`) all hard-code paths of the form `ai-docs/<feature-name>/<feature-name>-spec.md`, write retrospectives to `ai-docs/<feature-name>/<feature-name>-retrospective.md`, and invoke gate scripts via `python3 "$HOME"/.claude/fbk-scripts/fbk.py ...`. Several reference `.claude/fbk-docs/...` for their guides. The parent spec asserts the worktree's sparse-checkout reveals "only the in-scope paths" with `.firebreak/remediation/<cycle-id>/rearchitecture/**` always implicitly included. It does not commit to: where do per-module spec/task/retrospective artifacts live for a remediation cycle? Without this decided, every Feature 3, 4, 6, 7 child spec will re-litigate it, and the inclusion-manifest format cannot be authored against unknown path patterns. **Resolution**: in the runtime-precision block, add a "Per-module artifact paths under a cycle" entry that maps the existing `ai-docs/<feature>/<feature>-{spec,review,tasks,retrospective}.md` convention onto a per-module-per-cycle scheme (e.g., `ai-docs/remediation/<cycle-id>/<module-id>/<module-id>-spec.md`). Add an integration seam: "Reused skills → Worktree path resolution: every reused skill's `ai-docs/$FEATURE/...` references resolve under the per-module artifact root; gate-script invocation paths (`$HOME/.claude/fbk-scripts/fbk.py`) are exempt from tool-dispatch denial."

#### A3 — Move-list approval gate is described as "council pattern" but the spec doesn't pin the council-vs-spec-review boundary
**Severity**: important
**Description**: The reuse-vs-new boundary table lists move-list approval as `NEW (style on existing infra)` mapped to `/fbk-spec-review` council. But `/fbk-council` is general-purpose (no review document, no gate script), and `/fbk-spec-review` is keyed to a single `<feature>-spec.md` file with threat-model determination. The move-list is neither — it's a `move-list.yaml` plus typed contracts plus prose contracts. **Resolution**: pin the approach. Recommended phrasing: "The move-list approval gate is implemented as a new skill (working name `/fbk-rearchitect-review`) that follows `/fbk-spec-review`'s pattern: classifies perspectives, invokes `/fbk-council`, writes a review document, and runs a new gate script with rearchitecture-bundle-aware invariants. Not `/fbk-spec-review` itself because the input artifact set differs structurally."

#### A4 — "Firebreak engages" / "Firebreak reconfigures" markers map to unclear ownership in Feature 3
**Severity**: important
**Description**: The pipeline diagram introduces two named operations as visual divider rows, but their ownership is unclear. The "engages" marker sits *above* prep stage — is engagement (initial worktree+sparse-checkout setup) part of the prep skill, or separate? The "reconfigures" marker sits between code review and caller-update — hook? Operator step? Second invocation of `/fbk-remediation-prep` with a variant manifest? The first reconfigure conceptually engages the firebreak (worktree didn't exist); the second reconfigures sparse-checkout patterns. Different git operations (`worktree add` + `sparse-checkout init` vs `sparse-checkout reapply`). The diagram's symmetry hides the asymmetry. **Resolution**: in Feature 3 scope, add an "Operations owned by Feature 3" enumeration: (a) `worktree add` (cycle-start, once per cycle), (b) `sparse-checkout reconfigure for module rewrite` (per module, immediately before prep), (c) `sparse-checkout reconfigure for caller-update` (per module, after code review). State which skill or hook owns each.

#### A5 — Move-record `prerequisite-moves` and the cycle's per-module loop don't fully compose
**Severity**: important
**Description**: The 8-field move-record schema includes `prerequisite-moves` that "feeds wave-order computation," but moves and modules are not the same. A `merge` move has multiple `sources` and one `target`; the per-module loop iterates over modules, not moves. A `delete` move has empty `target` — does the loop visit it? Where does its caller-update happen? A `re-shape-interface` move whose `target` equals one of its `sources` (in-place) — one iteration or two? **Resolution**: add to runtime-precision a brief "Move → loop iteration mapping" sub-block (e.g., "each new or modified `target` module appears as exactly one loop iteration; `delete` moves have no iteration but their callers fold into the caller-update step of the move that *replaces* them; `re-shape-interface` with `source == target` maps to one iteration"). Or defer to Feature 4 with a sentence in the parent saying the mapping is owned there. Silence is the problem.

#### A6 — Cross-reference inconsistency: "caller-update wave" persists in §"Reuse-vs-new boundary" and Feature 8 scope after the per-module restructure
**Severity**: important
**Description**: The Decisions resolved during scoping entry **Caller-update timing** explicitly resolved to per-module incremental. The pipeline diagram and Feature 7's scope were updated. However: §Reuse-vs-new boundary table still lists a row "Caller-update wave | REUSED + tighter scope". A child spec for Feature 8 inheriting the parent verbatim would re-introduce the pre-restructure shape. **Resolution**: edit Feature 8 scope to match the per-module shape ("per-module pipeline × N modules (each iteration ending with that module's caller-update and atomic commit) → cycle retrospective"). Edit the Reuse-vs-new boundary row label to "Per-module caller-update step." Sweep for any other "caller-update wave" residue.

#### A7 — Retrospective-extension claim doesn't match what `retrospective-guide.md` actually does
**Severity**: important

The remediation flow's "cycle retrospective" is at a different granularity — covers a whole pipeline run across N modules. #### A8 — Feature 5 dependency update is correct, but the dependency-graph diagram's prose-vs-ASCII discrepancy weakens the document

#### A9 — Composability map is asserted as "load-bearing" but lives only in prose
**Severity**: important
**Description**: §Tech decisions / `/goal` composes only downstream of the firebreak says "The composability map is load-bearing — child specs must enforce it." #### A10 — Inclusion-manifest schema lacks a stage discriminator, but per-stage CLAUDE.md selection requires one
**Severity**: important
**Description**: Runtime-precision defines inclusion-manifest fields with naming `<module-id>.yaml` (default per module) and `<module-id>-caller-update.yaml` (variant). Per-module prep, breakdown, implement, and code-review are all distinct stages that may want different sparse-checkout patterns and CLAUDE.md selections, but the current schema collapses them. **Resolution**: either (a) commit to "one manifest per module covers prep, breakdown, implement, code-review; only caller-update gets a variant" with justification, or (b) extend manifest naming to `<module-id>-<stage>.yaml` with a default-fallback rule. Fix the cross-cutting prose to match the manifest schema's actual cardinality.

### Over-engineering / pragmatism

#### F-B1 — Six-layer "defense in depth" taxonomy is partly relabeling
**Severity**: important
**Description**: The six layers are not all distinct defenses. **Semantic** ("council deliberation at intent, rearchitecture, and spec review") is operator review with a council label — not a slop-specific defense. **Boundary** (tool-dispatch denial) is elsewhere demoted to "the floor… closes the residual gap"; listing it as one of six co-equal layers contradicts that framing. **Post-hoc** (retrospective fields) detects leaks after they happen, not "defenses against contamination passing through." **Resolution**: reduce to three real defenses — physical absence (worktree), lexical audit gates (agent-facing field hygiene), functional gates (scaffold-green, per-wave verification). Demote others to "supporting controls." Removes a downstream child-spec obligation: today every child spec must "identify which layers apply." Six layers × eight features × multiple stages = ceremony justifying the same handful of real mechanisms.

#### F-B2 — Triple-council ceremony (intent + rearchitecture + spec review) won't survive a real cycle
**Severity**: important
**Description**: Three council deliberations per cycle, plus existing per-module spec-review council × N modules, is a lot of council for a single developer. Feature 4's gate already requires "Council deliberation surfaces at least one move the operator did not propose" — that's the load-bearing council moment. Intent extraction is operator-first by design ("operator-first… recognition-over-recall"); a council on intent layers review on a stage explicitly framed as operator-driven. **Resolution**: commit to **one mandatory council per cycle, at rearchitecture (move-list approval)**, since rearchitecture is the spec's named "highest-stakes stage." Intent and per-module spec review use lighter operator review by default; council escalation is opt-in. Concentrate ceremony where the stakes actually are.

#### F-B3 — Feature 1.5 is a redundant gate without proportionate signal
**Severity**: important
**Description**: Feature 1.5 tests "many-to-many module remapping… produces better code than preserving original boundaries." But: Feature 1's outcome already informs whether the firebreak hypothesis holds — the architectural-decomposition hypothesis is independent. The merge-case test isn't load-bearing for Feature 2: if Feature 1 wins and merge-validation fails, the fallback only constrains Feature 4's scope. That's a Feature 4 design choice, not a project-stop signal. Adds another full pre-experiment commitment doc + blinded code review cycle, doubling validation latency. **Resolution**: either fold the merge case into Feature 1 (run two modules: one solo, one merge-pair, single retrospective) OR defer the merge-case validation to Feature 4's progress gate as a fixture test rather than a separate phase-gated experiment.

#### F-B4 — Operator recognition UX by stakes tier is premature design
**Severity**: important
**Description**: The spec commits to "Operator recognition UX by stakes tier (high one-by-one, medium batched, low bulk-confirm)" as a Feature 4 scope item, with `low | medium | high` baked into the move-record schema in the parent. We don't yet know what high-stakes vs low-stakes moves look like in practice. The three-tier UX presupposes a stakes distribution that justifies three review modes. It might be that 95% of moves are "medium" and the high/low buckets are rounding error. **Resolution**: keep the `stakes` field in the move-record schema (cheap, future-proof) but drop the three-mode UX commitment from Feature 4's scope. Replace with: "Move-list approval UX presents moves in stakes order; specific batching/grouping decided after Feature 1's manual rearchitecture surfaces actual move-volume and stakes-distribution data."

#### F-B5 — `GLOSSARY.md` as repo-wide infrastructure is scope creep
**Severity**: important
**Description**: The glossary is being adopted **repo-wide** as a Tech-decision-level commitment introduced by this project. Two pragmatism concerns: (1) **Scope creep**: a repo-wide artifact covering "all firebreak terminology" is being bootstrapped by a project that hasn't validated its load-bearing hypothesis. The hypothesis-gating discipline explicitly says "no tooling investment beyond Feature 1 until results land" — a glossary that gates `.claude/CLAUDE.md` and adds spec-review checks across all firebreak work is exactly the cross-cutting investment the gating discipline is meant to protect against. (2) **Necessity test**: the glossary's stated need surfaced from one term-naming question (interface stance). One naming problem doesn't justify a repo-wide artifact + a new spec-review check. **Resolution**: either scope the glossary to remediation-flow only (`ai-docs/remediation-flow/GLOSSARY.md`) and let the broader firebreak repo adopt it once a second project surfaces the same need, or keep the repo-wide commitment but explicitly mark it as a parallel workstream with separate justification.

#### F-B6 — Per-stage CLAUDE.md selection mechanism is two CLAUDE.md systems for one cycle
**Severity**: informational
**Description**: The spec commits to two CLAUDE.md regimes per cycle: a remediation-stage CLAUDE.md for above-firebreak stages, and a per-cycle CLAUDE.md inside the worktree for in-worktree stages. Right-sized **only if** the two contexts diverge meaningfully — and the in-worktree stages, by design, see only the rearchitecture artifact + new module skeleton. **Resolution**: when Feature 3's child spec lands, force the question — does the in-worktree CLAUDE.md need to differ from project-root? If not, drop the per-stage selection mechanism entirely. Flag this as something to actively try to eliminate when Feature 3 ships.

#### F-B7 — Inversion test mechanic is a gate criterion for something that may not exist
**Severity**: important
**Description**: Feature 4's scope lists "Inversion test mechanic," its gate says "Inversion test (if implemented) catches at least one contamination-preserving rearchitecture in test fixtures," and its fallback says "drop as a hard gate." Naming a gate criterion that's parenthetically optional is ceremony — neither a real gate nor a real scope item. **Resolution**: either commit to building the inversion test (remove "if implemented") with a clear definition of falsifiability, or remove it from Feature 4 scope and add to Feature 4 open questions. Conditional gate criteria are not gate criteria; they're aspirational notes pretending to be measurable.

#### F-B8 — Feature 6 (`/goal` integration) is a feature pretending to be one
**Severity**: important
**Description**: Feature 6's own fallback admits: "**Acceptable — architecture works without /goal**." If the architecture is whole without it, Feature 6 is an enhancement experiment, not a phase-gated feature. Making it a peer of Features 2–5 with its own progress gate, dependency declaration, and fallback paths overstates load-bearing-ness. **Resolution**: demote Feature 6 to an experimental task within Feature 8. Run end-to-end without /goal first; if successful, optionally try /goal as a follow-up to measure autonomy gain. Collapses 8 features to 7, removes a phase gate that doesn't gate the architecture.

#### F-B9 — Feature 5 placement is correct; tier model glossing earlier is unnecessary
**Severity**: informational
**Description**: The tier model is referenced in only three places before Feature 5 (runtime-precision enum, Feature 2 fallback, Feature 5 itself), and each reference is forward-looking ("defined in Feature 5") rather than depending on tier semantics. Pre-flight assessment correctly depends on Features 2–4's experience to calibrate tier heuristics. No change needed; pinning the **enum values** without committing to **what they mean** is appropriately minimal.

#### F-B10 — Hypothesis-gating discipline mostly holds, with one exception
**Severity**: blocking
**Description**: The spec commits to "no tooling investment beyond Feature 1 until results land," but the Decisions resolved during scoping block makes ~14 design commitments that pre-judge Features 2–8 before Feature 1 has run. Several are design ahead of evidence: move-record minimum schema, two-tier behavior inventory schema with controlled vocabularies, typed interface contracts as primary stub-generation mechanism, per-module incremental caller-update timing. Pinning these in the parent means every Feature 2–8 child spec inherits them rather than being free to redesign based on Feature 1's learnings. **Resolution**: before any child spec starts, add a section "Decisions revisitable after Feature 1" listing which resolved-during-scoping decisions are open to reconsideration based on Feature 1's experience, vs which are fixed regardless. Suggested revisitable: move-record schema, two-tier inventory schema, typed-contract requirement, per-module caller-update timing, council count. Suggested fixed: cycle ID format, ID stability rules, worktree-based isolation as primary firebreak (this one *is* the hypothesis itself).

### Measurability

#### F1 — Per-capita normalization methodology is undefined
**Severity**: blocking
**Description**: The spec says sightings are "normalized per deterministic codebase characteristic (LOC, function count, or similar)" with a "best-guess fresh-module floor," but does not specify: (1) the denominator (LOC vs function count vs cyclomatic-complexity-weighted-LOC produce materially different ratios on the same module pair); (2) the fresh-module floor methodology — what fixture(s), with which model/version, with what prompts, on what kinds of modules; (3) floor reproducibility for Features 1.5 and 8. **Resolution**: parent spec commits "denominator = function count from `<specific tool>`; floor = mean sightings/function across N (≥3) fresh modules generated from the operator's `[[realmind]]` typed-contract stubs by `/fbk-implement` on Claude `<model-id>` with default temperature; floor recomputed per major model upgrade." Belongs in the parent because the floor methodology is shared across Features 1, 1.5, and 8.

#### F2 — "Meaningful volume drop" threshold not pre-registered
**Severity**: blocking
**Description**: Highest-leverage measurement gap in the spec. The "different-bad-pathology" outcome is the only one that splits a project-stop from a project-continue based on a quantitative threshold, yet the threshold is the explicitly-named undefined term. Without pre-registration: operator sees results, then defines "meaningful" — confirmation bias structurally guaranteed. "Quantity" and "severity" are two axes — does either qualify, or AND/weighted? With no prior baseline of typical drops, the operator has no calibration: is 15% meaningful? 40%? 2x? **Resolution**: parent spec requires the pre-experiment commitment doc to fix a specific threshold expression — e.g., "≥40% reduction in per-capita sighting count AND distribution-shift Kolmogorov-Smirnov p<0.05" or "operator-pinned absolute number with stated rationale" — and explicitly forbids the commitment doc from being authored without that field populated. Currently the gate criterion lists "per-capita normalization defined" and "signal-axis rubric pinned" but not the volume-drop threshold as a required field.

#### F3 — Operator-judgment escape hatch lacks structural counter-pressure
**Severity**: important
**Description**: The spec is admirably honest that the gate is operator judgment and that operator mental-model contamination is unmitigated. But structural defenses against motivated reasoning are weak: a single operator (a) writes the commitment doc, (b) runs the experiment, (c) reads the blinded review output, (d) classifies the outcome, and (e) decides whether to continue the project they want to continue. The commitment doc is described as "forcing function … not a binding contract." **Resolution**: parent spec mandates at near-zero cost: (1) **pre-classify the data without seeing the outcome** — write the *classification rule* in the commitment doc as a decision tree so classification becomes mechanical given measurements; (2) **council classification, not solo classification** — invoke the Firebreak council on the post-experiment data with the commitment doc as input, require a council finding before the operator-of-record classifies; (3) **pre-register the alternative-hypothesis outcome shapes** — what specific finding-distribution would convince the operator the firebreak *failed*? If the operator cannot describe a falsifying outcome before the experiment, the experiment is unfalsifiable.

#### F4 — Feature 8's progress-gate numbers are unsourced
**Severity**: important
**Description**: The spec asserts three quantitative criteria as "load-bearing for whether the architecture works": "firebreak-leak rate <5%", "<20% of behaviors discovered during implementation that the inventory missed", "0 tasks widened scope beyond signature-mapping." None has a stated provenance. The **0 tolerance** for caller-update bleed is especially suspect — zero-tolerance gates over multi-task samples almost always get relaxed in practice. What sample size? If Feature 8 runs on 12 modules with ~3 caller-update tasks each, "0 of 36" is one observation away from failing. **Resolution**: each numeric criterion in Feature 8's gate carries either (a) a derivation from Feature 1/1.5 measured baselines plus a stated improvement target, or (b) an explicit "operator-set heuristic, recalibrate after first run" tag that prevents the number from being treated as load-bearing-evidence when it is load-bearing-aspiration. Plus: define the sample-size denominator for the `<5%` and `<20%` rates.

#### F5 — Outcome-class boundaries between adjacent classes are operationally fuzzy
**Severity**: important
**Description**: Two adjacent-class boundaries lack operational distinction. **`wins-but-misses-behavior` vs `different-bad-pathology with volume drop`**: both produce a rewrite that's structurally cleaner than the slop on the volume axis, but flawed elsewhere. A behavior the inventory missed *is* a different failure pattern (under-coverage rather than over-coverage). What measurement distinguishes them? **`similar-findings` vs `different-bad-pathology without volume drop`**: both stop the project, so the practical decision is the same — but the spec says "the distinction matters for the post-mortem." If the post-mortem distinction is operationally meaningful, the *measurement* must be defined. **Resolution**: a worked example in the commitment doc — given a hypothetical findings-distribution table for both slop and rewrite, the operator pre-commits to which class each row maps to. Converts boundary-classification from post-hoc judgment to pre-registered rule application.

#### F6 — Feature 4's "council surfaces ≥1 move operator did not propose" is a single-trial binary
**Severity**: important
**Description**: Single-trial binary criteria over a creative process are nearly always satisfied by chance. A council deliberation on any non-trivial move-list will almost certainly produce *one* move the operator didn't pre-list. This gate has no discriminative power. What it's *trying* to measure: the council adds value over operator-only authoring. **Resolution**: replace with a two-arm comparison or N-of-M acceptance rule grounded in a fixture size (e.g., "council surfaces ≥N moves not in operator's pre-list, and operator accepts ≥M of them as real improvements"), OR demote to informational and identify what actually gates Feature 4.

#### F7 — Feature 5's "fixture codebase set" is undefined
**Severity**: important
**Description**: ">75% match with operator's post-hoc assessment on a fixture codebase set" requires the fixture set to exist and be characterized. As written, the operator could: (1) pick the fixture set after seeing pre-flight outputs (selection bias), (2) make the fixture small enough that 3-of-4 = 75% (statistically meaningless), (3) author the post-hoc assessment after seeing pre-flight's recommendation (anchoring). "Post-hoc assessment" by the same operator who built the heuristics is itself a measurement-validity threat — the operator's heuristics encode their assessment intuitions. **Resolution**: parent or Feature 5 child spec specifies (a) fixture set composition (≥N codebases of types A/B/C, characterized along evidence-richness dimensions before pre-flight runs), (b) blinding protocol — operator records the post-hoc tier assessment *before* running pre-flight against that fixture, (c) sample size sufficient that the 75% threshold has a power-of-10 separation from chance.

#### F8 — Feature 6's "no false positives" gate has no defined denominator
**Severity**: important
**Description**: "No /goal false positives" with no sample-size denominator. Zero of one is "no false positives." Zero of one thousand is meaningful. The same Feature 6 gate also lists ">75% of trial cases" — so the denominator concept exists, just not applied consistently. **Resolution**: state the trial sample (e.g., "≥10 module-implementation runs across at least 3 module types") and apply it to both the >75% completion criterion and the false-positive criterion. Specify how false positives are detected — presumably by manually checking each /goal "complete" against the actual verification artifacts (a measurement cost).

#### F9 — Feature 2's recognition-rate corpus is undefined
**Severity**: important
**Description**: ">80% confirm/correct rate; <20% wholesale rejection" requires a corpus of hypotheses the operator scores. The corpus must be defined: how many hypotheses, generated against which subsystem, by which model, before scoring? Without this, the operator can pass the gate by selecting a small sample where 4-of-5 = 80%. The boundary between "correct" and "wholesale rejection" leaves the middle band ("partly right, edit needed") unspecified. **Resolution**: define minimum corpus size (e.g., ≥20 hypotheses across ≥2 representative subsystems), define the three-bucket scoring rubric explicitly with examples of edge cases, and pin the model used so re-running the gate is reproducible.

#### F10 — Retrospective measurement cost is unaccounted for in operator-time budgets
**Severity**: important
**Description**: Three of four new retrospective fields require non-trivial measurement labor: **firebreak-leak rate** = counting out-of-scope-read attempts (requires log retention infrastructure not specified anywhere); **move-list accuracy** = cross-referencing each behavior surfaced during per-module spec/breakdown/implement against the inventory (time-expensive); **caller-update slop signal** = identifying caller-update tasks that widened scope (manual diff review unless automated). If the operator-time budgets in Feature gates assume cycles run without measurement overhead, the gates will appear achievable in dry-runs and unachievable in real cycles. **Resolution**: each retrospective field carries a "measurement source" and an "operator labor cost" estimate, included in cycle-time budgets. Where automated tooling is required (firebreak-leak counting needs structured logs from tool-dispatch denial), name it as a Feature 3 or Feature 7 deliverable, not assumed-extant.

#### F11 — Pre-experiment commitment doc has no "invalidation" protocol
**Severity**: informational
**Description**: The spec says "mid-experiment tweaks are out of bounds" but does not address: what if the commitment doc itself was malformed (e.g., the operator realizes the per-capita denominator was wrong)? The current framing implies the operator must either (a) accept results under a flawed rubric or (b) declare the experiment invalid and re-run. Option (b) is a contamination vector — "this experiment was invalid, the *next* one will be definitive" can be invoked indefinitely. **Resolution**: parent spec adds a brief invalidation protocol — e.g., "experiment invalidation requires written rationale committed *before* outcome classification, with a recorded delay before re-running." Even small structural friction prevents easy soft-restart.

#### F12 — Feature 7's "median diff size, files touched" lacks a baseline

### Threat modeling

#### F-SEC-01 — "With care" is an unarticulated contamination vector across four pipeline stages
**Severity**: blocking
**Description**: The Cross-cutting "Per-stage CLAUDE.md selection" subsection and integration seams authorize pre-firebreak stages — pre-flight, intent extraction, rearchitecture, per-module spec, and per-module spec-review — to "reference dirty codebase with care" or "read it with operator discipline." This is exactly the prompt-level discipline the spec elsewhere argues *cannot* be the primary defense ("prompt-based read-discipline is exactly the mechanism CLAUDE.md uses to lose against 500 files of contrary signal"). The spec applies that argument to in-worktree stages but silently exempts the four highest-leverage above-firebreak stages from the same critique. "With care" is not an enforcement mechanism. Pre-flight is structurally defended ("external evidence only" + the External Evidence Principle); the other three are not. **Resolution**: parent spec must explicitly classify the above-firebreak stages as a known contamination surface, name the specific reads each stage is permitted (e.g., "intent extraction may read external docs, README, public interface signatures; may NOT read function bodies"), and either (a) declare a structural defense per stage or (b) explicitly accept the residual risk with a named mitigation.

#### F-SEC-02 — The "Semantic" defense layer (council deliberation) is itself contaminated
**Severity**: blocking
**Description**: Defense-in-depth lists "Semantic: council deliberation at intent, rearchitecture, and spec review." Council deliberation occurs at stages where agents are explicitly authorized to read the dirty codebase (per F-SEC-01). Council members are LLM agents. If those agents have read slop above the firebreak, their deliberation is shaped by the same pattern-matching the Vision identifies as the failure mode. The spec asserts council adds a defense layer but does not articulate the mechanism: how does deliberation defend against contamination when the deliberators themselves are exposed? **Resolution**: either name the specific contamination-defense mechanism council provides (clean-witness role, adversarial-decomposition pass at intent that operates only on agent-facing fields) or move council deliberation out of the defense-in-depth list and into "process quality." Process is valuable; calling it a defense layer when it has no articulated threat-defeat mechanism is named-but-not-defending.

#### F-SEC-03 — "Functional" layer conflates correctness gates with contamination defense
**Severity**: important
**Description**: Defense-in-depth names "Functional: scaffold-green gate, per-wave verification, baseline regression, final verification." These are correctness gates against compile/typecheck/test failures. They defend against bugs, not against contamination. A perfectly-typechecking, fully-test-passing module can still encode slop-shaped abstractions, control-flow shapes, and naming patterns inherited from the original. The spec's own Vision is built on this premise: contamination is structural, not behavioral. Counting these as defense layers conflates two different threat models and inflates the apparent depth of contamination defense. **Resolution**: either rename to "Behavioral correctness" and acknowledge it defends against a different threat (regression / behavior loss), OR articulate the specific contamination patterns these gates *do* catch (e.g., "scaffold-green prevents the agent from carrying forward stale import paths because uncompilable imports fail the gate" — if true).

#### F-SEC-04 — "Post-hoc" layer is detection without prevention; mislabeled as defense
**Severity**: important
**Description**: Defense-in-depth names "Post-hoc: cycle retrospective with architecture-decision, firebreak-leak, move-list-accuracy, and caller-update-bleed fields." Retrospective fields are forensics — they measure how much contamination got through after the cycle has already shipped its work. By Feature 8's progress gate, a firebreak-leak rate <5% is the success criterion, which means up to 5% leakage is *expected* and the retrospective merely counts it. A post-hoc count that triggers no rollback, no quarantine, and no automated re-review is not a defense layer in the conventional sense — it's a feedback signal for the next cycle's design. **Resolution**: either rename to "Detection / measurement" and remove from defense-in-depth, OR articulate what corrective action the retrospective *triggers* automatically (rollback threshold, mandatory re-review at >X% leak rate). Without a corrective trigger, "post-hoc" defends nothing operationally.

#### F-SEC-05 — Worktree physical-absence claim has unenumerated escape paths
**Severity**: blocking
**Description**: The Tech decisions section makes the foundational claim that "the slop codebase is not physically present in the worktree — it isn't denied, it isn't there." The spec does not enumerate the structural escape paths, all real for a `git worktree add` + `git sparse-checkout` setup: (1) **Symlinks pointing outside the worktree** — sparse-checkout governs what's *checked out from git*; symlinks already in the working tree to absolute or `..`-relative paths outside the worktree resolve normally on read. (2) **Git history access** — `git show <sha>:path/to/slop/file.py`, `git log -p`, `git blame` against the remediation branch can return slop content even when sparse-checkout hides the working-tree file. The slop is in the git object database, not just the filesystem. `Bash` tool calls can invoke any of these. (3) **`Bash` tool path traversal** — the spec mentions tool-dispatch denial against `Read`/`Grep`/`Glob` but does not address `Bash`. `cat ../../../slop/file.py`, `find / -name '*.py'`, `grep -r 'pattern' /home/...` all bypass the sparse-checkout view. (4) **Build configs with absolute paths** — `pyproject.toml`, `tsconfig.json`, `Makefile`, env files referencing absolute paths to slop locations. (5) **Cached file content in agent context** — multi-turn sessions where the agent read slop in an earlier turn carry the content in transcript memory; worktree absence does not unread it. (6) **Sparse-checkout misconfigurations** — a pattern like `*` reverts to a full checkout silently. The inclusion-manifest schema needs validation rules. **Resolution**: Feature 3's child spec (or this overview) must enumerate the escape paths and declare for each: (a) blocked by tool-dispatch denial with the specific deny rule, (b) blocked by inclusion-manifest validation with the rule, (c) accepted residual risk with rationale and the post-hoc detection that catches it, or (d) operator-discipline-only (called out explicitly).

#### F-SEC-06 — Tool-dispatch denial scope is undefined; `Bash` is the elephant
**Severity**: blocking
**Description**: The spec mentions tool-dispatch denial as a floor but never specifies its surface. Feature 3's progress gate says the floor catches absolute-path escapes "in a test harness (`Read`, `Grep`, `Glob`)" — exactly three tools. There is no mention of `Bash`, `Edit`, `Write` (against absolute paths outside worktree), `Task` (subagent launches that may not inherit the same permissions hook), `WebFetch`/`WebSearch`, or skill/agent invocations that themselves perform reads. `Bash` is the load-bearing concern: any general-purpose shell command can read any file the user has permission to read. If `Bash` is not denied or sandboxed at the firebreak, the floor is ankle-high. **Resolution**: Feature 3's child spec must declare the exact set of tools and tool-call shapes the denial floor covers, with a per-tool decision and rationale. The most defensible model is allowlist-by-default for in-worktree stages. The implementation surface (hook, per-tool wrapper, settings.json `permissions` block) and bypass surface (subagent inheritance, skill-defined tool calls, /goal-driven invocations) should both be named.

#### F-SEC-07 — Operator mental-model contamination is acknowledged but unscoped beyond Feature 1
**Severity**: important
**Description**: Feature 1 explicitly acknowledges operator mental-model contamination as an "unmitigated threat to validity" and notes "Feature 2's child spec considers whether intent extraction needs structural defenses against operator-articulated slop becoming ground truth." That's a forward reference, not a project-level scoping commitment. The architecture is operator-first at intent extraction. If the operator's mental model is contaminated, their stated intent — the load-bearing input to rearchitecture, which is the load-bearing input to everything downstream — carries the contamination forward through the firebreak structurally. The firebreak is an excellent defense against contamination *via the codebase*; it provides zero defense against contamination *via the operator*. Every layer past intent inherits whatever shape intent encoded. **Resolution**: parent spec adds a cross-cutting concern naming operator mental-model contamination as a project-level residual risk, names the structural defenses considered (e.g., council adversarial-hypothesis prompts at intent, recognition-over-recall UX as partial defense, blinded retrospective re-review by operator after time gap), and explicitly accepts the residual risk with rationale.

#### F-SEC-08 — `/goal` restriction is described as load-bearing but enforcement mechanism is undefined
**Severity**: important
**Description**: "/goal is therefore restricted to under-the-firebreak stages... The composability map is load-bearing — child specs must enforce it." The threat model is articulated correctly (worker reads of slop pollute the transcript; evaluator confirms false positives). The enforcement mechanism is not. "Child specs must enforce it" pushes the enforcement burden down without naming the mechanism — which means in practice it relies on operator discipline. If the operator could conceivably invoke `/goal "complete intent extraction"` at intent extraction, what stops them structurally? **Resolution**: name the enforcement surface in the parent spec — most likely a hook that inspects the current working directory at `/goal` invocation and refuses if it's not inside `.firebreak/remediation/<cycle-id>/worktree/`. If "operator discipline only," state that and accept the residual risk explicitly.

#### F-SEC-09 — Refusal protocol override surface is undefined
**Severity**: important
**Description**: Feature 5's progress gate says "Refusal protocol is structurally enforced (operator cannot bypass without explicit override)." The "explicit override" mechanism is not specified. For a single-developer project, "explicit override" can range from a CLI flag to a multi-step confirmation requiring rationale to a hard refusal that requires editing source. The threat is not external — it's the operator under deadline pressure overriding their own safety check. The structural defense should make override *frictionful enough that it's a deliberate decision*, not a `--force` flag muscle-memorized. **Resolution**: Feature 5's open question on override mechanism should be elevated to a parent-spec scoping decision since it intersects with the project's overall refusal-protocol stance. Recommended pattern: override requires the operator to write a rationale (matching the wave-order override pattern, where override requires a comment line stating rationale).

#### F-SEC-10 — Terminology hygiene as contamination defense is asserted, not evidenced
**Severity**: informational
**Description**: The Tech decisions and GLOSSARY decisions make a strong claim: "Every term used in remediation-flow artifacts shapes downstream agent behavior." This is asserted as foundational and is the basis for promoting GLOSSARY.md to first-class repo infrastructure. The claim is plausible and matches LLM-priors intuition. It is not, however, evidence-based in the spec. There is no reference to empirical observation, no link to a wiki entry establishing the pattern, no measured impact. **Resolution**: either acknowledge "this is an operating hypothesis the project will validate via observation" with a placeholder for evidence as cycles run, OR cite the source establishing the claim. Additionally, consider whether terminology hygiene should be a 7th defense-in-depth layer ("Linguistic" — applied at every text-output stage) rather than absorbed into Lexical/Structural.

#### F-SEC-11 — Lexical/structural audit gates have no false-positive/false-negative characterization
**Severity**: informational
**Description**: The Lexical/Structural defense layer is the most concrete in the list — audit gates against current module names, controlled vocabularies, domain-language patterns. Feature 2's gate says these audits are checked. The spec does not characterize what these gates *miss*: a behavior described in pure domain language can still encode slop-shaped granularity (e.g., one behavior per slop function, when the right inventory has one behavior per domain concept covering multiple functions). The gates catch surface contamination but not granularity contamination. **Resolution**: Feature 2's child spec should articulate which contamination patterns the audit catches (named: module names, CamelCase, slop-style function names) and which it does not (granularity, abstraction-level, missing vs over-decomposed inventory entries). The latter category is what the recognition-rate criterion is implicitly defending against.

## Threat model determination

**Decision**: skip — no formal `remediation-flow-threat-model.md` artifact authored at this stage.

**Security-relevant characteristics summary**:
- **Data touched**: source code (the operator's own codebase being remediated). No PII, no credentials, no external user data.
- **Trust boundaries crossed**: filesystem boundary between the operator-managed remediation branch's working tree and the worktree's sparse-checkout view; tool-dispatch boundary between agent tool invocations and the actual filesystem.
- **New entry points**: new skills (`/fbk-remediation-intent`, `/fbk-rearchitect`, `/fbk-remediation-prep`, `/fbk-remediation-preflight`); the operator-managed remediation branch as a workflow entry point.
- **Auth/access control changes**: none in the classical sense. The "access control" is contamination defense — controlling which paths are visible to which agent at which stage.
- **Primary "threat actor"**: AI-slop contamination in the operator's codebase, not an external adversary. The architecture is structurally security-shaped (defense-in-depth, trust boundaries) but the threat model is contamination, not malicious actors.

**Rationale for skipping**: the Security perspective surfaced 11 findings in this review (3 blocking, 4 important, 4 informational) that carry the project-level threat awareness without a separate document. The blocking security findings (F-SEC-01 above-firebreak contamination surface, F-SEC-02 contaminated council layer, F-SEC-05 worktree escape paths, F-SEC-06 tool-dispatch denial scope including `Bash`) are the load-bearing threat-model gaps; resolving them in the parent spec or Feature 3 child spec is more useful than capturing them in a parallel artifact. Child specs (especially Feature 3 for worktree firebreak infrastructure) will author per-feature threat-model sections as needed. Authoring a formal STRIDE-style document before Feature 1 validates the firebreak hypothesis would be investment ahead of evidence — exactly what the project's hypothesis-gating discipline guards against. If Feature 1's outcome supports continuation, Feature 3's child spec is the right venue for systematic threat-model authoring.

## Overall assessment

The spec is structurally sound at the high level. The blocking findings split into two cohorts:

**Must-fix-before-child-specs-start (architectural and security):**
- A1 (wave terminology collision) — child specs will inherit two meanings of "wave"
- A2 (path conventions for reused skills under the worktree) — Feature 3 child spec cannot author the inclusion-manifest format without this
- F-SEC-01 (above-firebreak "with care" stages as unarticulated contamination surface) — child specs for Features 2 and 4 will inherit the gap
- F-SEC-02 (Semantic defense layer is contaminated) — undermines the defense-in-depth claim that child specs reference
- F-SEC-05 (worktree physical-absence escape paths unenumerated) — Feature 3 child spec needs the catalog
- F-SEC-06 (tool-dispatch denial scope undefined; `Bash` not addressed) — Feature 3 child spec cannot author the floor without this

**Must-fix-for-the-validation-experiment-to-be-interpretable:**
- F1 (per-capita normalization methodology undefined) — Feature 1's load-bearing measurement instrument
- F2 (meaningful volume drop threshold not pre-registered) — the gate criterion for the only outcome class with a quantitative split
- F-B10 (hypothesis-gating discipline pre-judges Features 2–8 in resolved-during-scoping) — without an explicit "decisions revisitable after Feature 1" commitment, the discipline is rhetorical

The 26 important findings are recoverable but cause moderate rework if missed. The 7 informational findings are documentation polish.

The cross-agent convergence on defense-in-depth being inflated is the strongest signal in this review — three of six named layers don't actually defend against contamination per the spec's own definition. Trimming the taxonomy to three real layers + supporting controls would simultaneously address F-B1, F-SEC-02, F-SEC-03, F-SEC-04, and reduce the cross-cutting child-spec obligation that comes with the six-layer claim.
