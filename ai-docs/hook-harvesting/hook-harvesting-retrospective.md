# Retrospective: deterministic metrics plane (hook harvesting)

## Timeline

- **Intent** — started and completed 2026-06-10.
- **Design** — started and completed 2026-06-10.
- **Spec** — started and completed 2026-06-10.
- **Spec Review** — started and completed 2026-06-10 (one revision; a second verification pass closed all blocking findings).

## Key decisions

1. **Both capture sources ship in v1** (Intent) — the brief contradicted itself on whether the Claude-level hook router was in scope; the operator resolved it to include both the router and the Python-layer instrumentation, which pulls privacy gating, capture levels, and retention into v1.
2. **Globally armed, per-project gated capture** (Intent) — recorded as a governing constraint in the decisions log and architecture overview. Rationale: privacy, ambient overhead, and sandbox read-only mounts.
3. **Three capture levels with `standard` as the shipped default** (Intent) — operator chose to commit the default now rather than defer it; payloads (tool args, prompt text) are captured only at `full`.
4. **Report runs ad-hoc and auto-injects at retrospective** (Intent), with a machine-generated provenance marker so the table is auditable as machine-written.
5. **Token/cost harvesting is in v1** (Intent), run post-hoc against transcripts and joined to stages via state timestamps.
6. **Retention bounded by an automatic size/age cap** (Intent); exact threshold deferred to design.
7. **Operator-locked baseline protection for retention** (Design) — a ~5MB size cap prunes oldest events but skips any spec named by a lockfile in `.fbk-capture/locked/`, reconciling the bounded-file requirement with the before/after comparison use case.
8. **Gate pass rate reported as two rows** (Design) — first-try and after-rework rates kept separate rather than blended, so clean-pass behavior and rework-recovery behavior are distinguishable.
9. **Per-stage deterministic retrospective injection at the state transition** (Design) — overrides the intent-phase "auto-inject at retrospective" framing: the operator clarified retrospectives are appended at multiple stage boundaries and cannot be operator-run, so the metrics block is injected from `transition_state()` on each stage completion, with the agent's prose layered alongside.
10. **Single shared events file; capture.cfg holds the level** (Design) — one `.fbk-capture/events.jsonl` with spec as a field; capture level lives in a dependency-free key=value file read on the hot path, not in the YAML config surface.
11. **Report and harvester live flat, not in new packages** (Spec) — the report command is `fbk/report.py` and the harvester is `fbk/capture/token_harvester.py`, rather than the design's tentative `fbk/commands/` and `fbk/harvest/` packages, to match the existing flat single-command convention and keep the harvester inside the capture subsystem.
12. **Retention is a size cap only** (Spec) — the events file self-prunes at a ~5MB size cap with no age cap; the before/after-comparison use case is protected by the baseline lock, not by recency, so a second age threshold would only add a tunable and a second way a forgotten baseline could vanish.
13. **Retrospective path reconciled** (Spec) — the injector resolves `ai-docs/<spec>/<spec>-retrospective.md` from `os.getcwd()`, the exact path the retrospective skill and existing `append_section` callers use, closing the design's flagged path-mismatch item so the machine block and agent prose share one file.
14. **Dedicated threat model produced** (Spec Review) — the operator chose to build the structured artifact given a global hook that can capture prompt text gated only by a filesystem check; it seeds the absent project-level threat model. Three blocking spoofing/disclosure threats were found that inline ACs had missed.

## Scope changes

- The brief's framing of the hook router as a "separate, generic tool" (a non-goal for v1) was overturned during the interview: the router is in v1.
- The shipped default capture level, which the brief deferred to an empirical call during development, was committed at intent time to `standard`.
- The retrospective-injection mechanism shifted at design from "auto-inject when the retrospective phase runs" (PRD framing) to per-stage injection wired into the state transition, after the operator clarified there is no single operator-run retrospective phase.

## Stage 1: Intent

**What the work is and why.** Firebreak's only performance record is the agent-appended retrospective — anecdotal, undenominated, unreliable under context pressure, and unqueryable. The feature replaces narration with deterministic, machine-recorded events captured from code and aggregated into a report the agent interprets rather than authors. This makes before-and-after evaluation of rework-reduction features possible without an expensive full benchmark run.

**Interview decisions** (full record in `grilling-log-intent.md`): v1 scope (router + Python layer), report timing (ad-hoc + auto-inject), token harvest in scope, three capture levels, `standard` default, size/age retention cap, and the globally-armed/per-project-gated privacy model confirmed as a standing constraint.

**Artifacts produced.** `prd.md` (10 sections), `behavior-inventory.yaml` (17 behaviors, B-001…B-017), `grilling-log-intent.md`, `fresh-eyes-intent.md`.

**Fresh-eyes.** Three cold-review rounds. Round one raised two Criticals (the "written by report not agent" criterion was unauditable; the token harvester assumed transcripts always present). Round two, after fixes, raised two more (parks and rework had no named capture source). Both were closed by making explicit that parks and rework derive from the state engine's existing park/error history and stage-timestamp re-entry — no new logging. Final round returned an empty Critical section. The surviving Substantive/Minor observations are design-phase mechanism choices (kill-rate counting rule, gate-attempt attribution under rework, intra-session token attribution, provenance-marker format, park-reason form) carried into `/fbk-design`.

**Open questions deferred to design.** Single shared event store vs. per-spec files plus merge; gate-result envelope shape (summarized vs. verbatim); where the capture setting and explicit capture marker live; exact retention threshold and its reconciliation with cross-cycle comparison; the source and freshness of the known-Firebreak-agent list.

**Process note.** The seed brief was unusually complete — it carried audit findings and measured experiment results from a prior `/opt/code` capture session. That front-loading meant the interview resolved scope forks quickly, but it also embedded a latent self-contradiction (router in vs. out) that only surfaced under questioning. Worth remembering: a thorough brief still needs its scope boundary stress-tested, because completeness can hide contradiction.

## Stage 2: Design

**Module shape and contracts proposed.** The plane decomposes into a capture package (`fbk/capture/`) — shared event writer, schema/vocabulary with a drift check, per-project capture gate, the globally-installed hook router, the dispatch-chokepoint recorder, retention pruner, known-agent filter, and the retrospective injector — plus a report command (`fbk/commands/report.py`) and a post-hoc token harvester (`fbk/harvest/`) ported from the validated prototype. Five design pages (overview, capture-sources, reporting-and-injection, configuration-and-lifecycle, contracts) organize these by capability boundary. Ten contracts (IF-D-01…IF-D-10) record the event envelope, the writer, the capture gate, the chokepoint wrapper, the capture-config and round-log file formats, the stage-summary/injector pair, the retention pruner, the provenance marker and retro path, and the known-agent set.

**The three hard seams.** Most boundaries were clean; three were not and drove the design. The chokepoint must capture a gate's stdout JSON without breaking the print-then-`sys.exit()` contract — resolved with an explicit save-buffer-`try`/`finally`-restore-and-re-emit mechanism. Code-review round data lives only in the agent-orchestrated skill, not the deterministic gate — resolved with a file handoff (`.code-review-rounds.json`) the skill writes and the gate reads. Token-to-stage attribution has no transition record inside a transcript — resolved with a hard split on state-engine transition timestamps.

**Decisions appended to the durable log.** Eleven design-phase entries in `docs/decisions-log.md` (2026-06-10): chokepoint stdout capture, gate-result summarized-vs-verbatim by level, single shared events file, capture.cfg location and marker, known-agent list derivation, token attribution hard-split, code-review round-log handoff, retention with operator-lockable baselines, two-row gate pass rate, kill-rate counting rule, and per-stage retrospective injection. Four were operator rulings surfaced one at a time (retention, gate pass rate, retro trigger, kill-rate); the operator's retro-trigger answer overrode the architect's recommended operator-run command.

**Decomposition rationale.** Vertical slices by capability boundary — each page owns a capability a reader reasons about as a unit (where events originate, what consumes them, how the plane is governed), with a separate contracts page for the schemas that cross process and trust boundaries.

**Fresh-eyes.** One adversarial round surfaced five Criticals, all resolved before the gate: the state transition had no path to the project root (resolved by `os.getcwd()` convention); the working-stage injection predicate was undefined against the real uppercase state names (resolved by deriving the eight PARKED-capable states from `VALID_TRANSITIONS`); a resume-to-working transition would have skipped injection (resolved by firing on stage completion, which covers rework for free); the stdout re-emit mechanism was imprecise under `SystemExit` (resolved with the `finally`-flush specification); and the verification hook's dispatch path was unstated (clarified — it routes through `fbk.py task-completed`, so the chokepoint sees it). Substantive and minor observations (intent-phase deferrals, heading-collision, drift-check-vs-discard layering) were all folded into the pages.

**Process note.** The fresh-eyes pass earned its keep here: its catches were almost all about the design's claims not matching the *actual* Firebreak source — the real `transition_state` signature, the real state names, the real dispatch path. The lesson echoing the intent stage: an architect reasoning from a clean mental model will state integration claims that are plausible but wrong against the code, and only a read against the real files catches them. One genuinely unresolved item is consciously deferred to spec: the retrospective filename convention (`<feature>-retrospective.md`) must be reconciled with the injector's path resolution before implementation.

## Stage 4: Spec Review

**Perspectives invoked.** Four council agents in discussion mode — Architecture, Security (Threat modeling), Quality (testing strategy and impact), and Measurability — plus the independent CP1 test reviewer. Builder and Advocate were deliberately omitted: pragmatism and scope were largely settled at intent, and the operator-facing surface is small. Each perspective was instructed to read the spec against the *real* `fbk-scripts` source, not just the design. A dedicated threat model was produced (operator decision) at `hook-harvesting-threat-model.md`.

**First-pass outcome: fail, returned to spec.** The first pass found roughly eleven blocking findings across the four concerns plus the test reviewer. The unifying theme is the same one that recurred at intent and design, now sharper: the spec described its integration surface against an idealized version of the code. Verified-against-source examples: the installer it targets (`assets/fbk-scripts/install.sh`) does not exist (the real one is `installer/install.sh` + `installer/merge-settings.py` + the `assets/settings.json` template, whose merge engine is add-only and cannot perform the assigned duplicate-removal); the "retired tests" the audit-retirement slice names do not exist (neither gate test asserts `audit.log_event`, so the call-site swap would ship untested); the injection predicate keyed on previous-state-only fires on *park* as well as completion, contradicting its own acceptance criterion; and a third `audit.log_event` call site (in the dispatch-status hook) went unenumerated.

**Blocking findings by theme.**
- *Privacy/security (three threats with concrete attack paths):* the capture gate keys on the bare presence of `.claude/automation/` — a shared namespace — so a hostile repo can ship a marker plus a full-capture config and record the operator's prompts on open; the router's working-directory provenance is unpinned, so gate-dir and write-dir can diverge under attacker influence; a symlinked capture dir or config escapes the gitignore confinement the whole model rests on.
- *Correctness:* the injection-on-park predicate bug (traces back into the design); the installer reality gap.
- *Measurability (the feature measures things, so its own metrics must be sound):* the first-try/after-rework "rate" has no defined denominator; the kill-rate's documented bias is neither surfaced to consumers nor pinned by a value test; the token hard-split's "error identical across cycles" — the load-bearing assumption for the headline before/after use case — is asserted, never measured.
- *Testability:* the audit-swap ships untested; the router's write-location guarantee (never the global config dir) and its process-level fail-silent path are both untested.

**Spec revisions and iteration count — one full iteration.** The operator chose to revise rather than accept or triage. The revision closed all eleven blocking findings plus the important and informational ones, added seven new acceptance criteria (AC-21–AC-27, mostly the security and confinement guarantees), and crossed back into the design artifacts for the two items that were design defects (the injection-on-park predicate and the installer's add-only merge engine). A second verification pass — the same four perspectives plus the test reviewer, each handed only its own prior findings and pointed at the *revised* spec and the *real* source — confirmed every blocking finding closed.

The second pass earned its keep twice over. First, it caught a **regression the fix itself introduced**: the new "don't honor full from a git-tracked config" mitigation was silently defeated by the new "writer self-creates a `*` gitignore" mitigation — every in-tree config now reads as gitignored, so git-tracked-ness could no longer distinguish operator-authored from repo-shipped, and the only correct check (a git-index query per tool call) blew the hot-path budget. The resolution was to stop using git-tracked-ness entirely and gate the privileged `full` level on an operator-controlled signal *outside the repo working tree* that a cloned repo cannot ship. Lesson worth keeping: a security fix can introduce a security hole by interacting with another fix, and only a second adversarial pass over the *revised* artifact catches it — the first pass cannot review edits that do not yet exist. Second, it caught spec-leads-design reconciliation debt (the design pages still carried the superseded module homes and the unhardened gate invariant), which was then fixed so the design no longer contradicts the authoritative spec.

**Both gates pass; result pass after one revision.** The review and threat-model gates pass structurally, and the substantive verdict is now pass. The threat model artifact (`hook-harvesting-threat-model.md`, gitignored) seeds the project's first threat model via its proposed-updates section, pending operator approval.

**Process note.** The decision to instruct every perspective to read the *real source* rather than only the design and spec is what produced the high-value findings — every blocking correctness and testability finding was a claim that read as plausible in the spec and was false against the checked-in code. This is now the third consecutive stage (intent fresh-eyes, design fresh-eyes, spec review) where the dominant failure mode was prose-plausible-but-code-wrong, and the dominant control was a grounded read. Worth carrying as a standing expectation: for brownfield features, a review that does not open the modified files is not a review. The second lesson is narrower and about the gate: the review and threat-model gates check *structure* (perspectives present, severities tagged, threat-model sections, three testing categories), not whether blocking findings are resolved — so a structurally-passing gate with a fail verdict is the expected, correct state when the work genuinely needs another pass.

## Stage 3: Spec

**How thoroughly the design pre-resolved the work.** This was the most front-loaded spec entry to date: the approved design had already pinned ten interface contracts, the exact stdout-redirect mechanism, the injection predicate against the real state machine, and the kill-rate and token-attribution rules. The spec phase was therefore mostly faithful transcription plus closing the two items the design left for spec time — not fresh design. This is the intended shape when the design phase does its job; the spec's value here was grounding every contract reference against the real `fbk-scripts` source and minting the contracts the design described only as modules.

**Clarifying questions that resolved ambiguity** (narrowed to "how," per the spec phase's remit). Two operator-resolvable choices were raised and answered: (1) where the report command and token harvester live — the operator chose flat `fbk/report.py` and `fbk/capture/token_harvester.py` over the design's tentative new `fbk/commands/` and `fbk/harvest/` packages, aligning with the existing flat-command convention; (2) the retention cap shape — the operator chose a size cap only, leaving age out. The design's one flagged spec-time item, the retrospective path mismatch, was resolved by inspection rather than by asking: the skill's convention (`ai-docs/<spec>/<spec>-retrospective.md` from `os.getcwd()`) is exactly what the injector computes, so there was no conflict to put to the operator.

**Scope inclusions/exclusions.** Included: a module touch policy naming every existing file the feature changes (`fbk.py` and the two audit-call gates as refactor-then-extend; `state.py`, `task_completed.py`, `code_review.py`, `install.sh`, and the code-review skill as extend; `retro.py` and `audit.py` left alone). Excluded explicitly: retiring the old per-spec audit log (its two call sites move to the event writer, but the `.log` files and the `audit` module stay for backward compatibility). Three spec-originated contracts were minted for interfaces the design named as modules but did not pin — the token harvester, the report command, and the installer migration.

**Slices.** Ten slices, every behavior B-001…B-017 covered. Most are `new-contract`; the chokepoint-and-audit-retirement slice is `contract-evolving` and carries the only retired tests (the two gates' `audit.log_event` call assertions), and the end-to-end-seam slice is `cross-cutting`.

**Open questions deferred.** None. The PRD's five design-deferred questions were all resolved in design; the design's one spec-deferred item was resolved here. Section 8 is empty.

**Process note — the gate enforces design-to-spec fidelity, and that caught real omissions.** The first gate run failed not on prose quality but on structure: it demands every design contract be carried into a `## Interface contracts` section (or explicitly excluded with rationale) and every acceptance criterion be covered by a contract's covers list. That forced two things the draft had skipped — carrying all ten `IF-D` contracts verbatim, and minting `IF-S` contracts for the harvester, report, and installer so their acceptance criteria had a contract home rather than floating. The gate also rejected numbered section headings (`## 1. Problem`) because it matches exact heading prefixes. Worth remembering: the spec gate is not a prose check, it is a traceability check — design contracts to spec contracts to acceptance criteria to integration seams must form an unbroken chain, and the draft's readable-but-untraceable first pass did not satisfy it.

## Stage 5: Breakdown

**Result.** 37 tasks across 6 waves — 21 test tasks and 16 implementation tasks. Both deterministic gates pass (task-reviewer and breakdown), the checkpoint-2 test reviewer returned accepted, and zero bounce-back markers remain. The compilation followed the slice-then-pair shape: one test task plus one implementation task per `new-contract` slice, and a test-only pair-less task for the single `cross-cutting` slice.

**Slice disciplines, as finalized.** Nine of the ten slices are `new-contract`; the tenth (end-to-end-seam) is `cross-cutting` and correctly produced seam tests with no paired implementation task. Worth correcting the Stage 3 note above: the chokepoint-and-gate-event-logging slice is **not** contract-evolving and retires **no** tests — the spec review verified that neither gate's existing tests assert the old `audit.log_event` call, so the migration adds new envelope-write assertions rather than retiring any. The breakdown carries that forward: there is no `retired_tests` list anywhere, and no pre-existing test is hash-locked at breakdown time (all coverage is net-new), so the pre-lock hash population is deferred to implementation as designed.

**Codebase grounding surfaced one real spec-vs-code gap.** The spec prose says "two existing `audit.log_event` call sites in the spec and task-reviewer gates," but the real code has three physical sites: `spec.py` logs on both its fail path and its pass path, and `task_reviewer.py` logs once on pass. The code is authoritative, so the migration task covers all three; the fourth caller in `dispatch_status.py` deliberately stays on the old path. This is the kind of undercount that only a grounded read catches — consistent with the standing brownfield lesson from the prior stages.

**Eleven bounce-backs, all resolved at compile time without returning to spec.** The test-task agent was correctly walled off from `design/contracts.md` — the document the spec names as the authority for exact signatures — and so it conservatively flagged eleven interfaces it could not pin (the token-harvester entry point, the report's computation helpers, the redactor's field set, the known-agent scan-root override, the out-of-tree `full` signal, the retention over-cap channel, and several test-mechanics seams). None were genuine spec defects: every one was resolvable from the design contracts, the named prototype, the real code, or a compilation-time implementation choice the compiler is empowered to make. Three were genuine choices and are recorded as such — the duplicate-registration removal lives in `merge-settings.py` as a callable function (testable) rather than buried in shell; the retention over-cap warning surfaces through a durable `.fbk-capture/.retention-warning` sentinel the report reads; and the report exposes importable pure helpers (classification, first-try rate, kill rate, park/rework derivation) because the spec's own unit tests demand exact-value assertions on them. The resolved signatures were fed to both the test and implementation agents verbatim so the two halves share one interface.

**Two structural adjustments during assembly.** First, the shared test-fixture builder needed its own earliest wave: it is consumed by several foundation-level tests that would otherwise sit in the same wave, and a dependency must resolve to a strictly earlier wave. Pulling fixtures into wave 1 alone, with the foundation primitives at wave 2, fixed it. Second, the repository is split-root — the Python package lives under `assets/fbk-scripts/` while the installer, settings template, and code-review skill sit at the repo root — so no single project root let the task-reviewer gate's file-existence check resolve every path. Rewriting the package paths to repo-root-relative (`assets/fbk-scripts/...`) gave one consistent anchor and, as a bonus, aligned the verification hook's out-of-scope check, which compares against repo-root-relative git-diff paths.

**Two test/implementation consistency fixes the impl agent caught.** The fixture builder stamped `schema_version` as the integer `1` while the writer's envelope uses the string `"1.0"` — corrected to match the writer. And the verification hook's out-of-scope file *paths* are a free-text payload that central redaction strips at `standard` (AC-26), so the test asserting the path list now runs the project at `full`; the non-free-text counts survive at any level.

**Checkpoint-2 test review: accepted with three applied refinements.** The reviewer confirmed all 27 acceptance criteria are backed by behavioral (not surface) assertions, no owned code is mocked as a test's primary subject, and the red phase holds. Three non-blocking findings were applied rather than deferred: the end-to-end test stopped one transition short of firing the retrospective injector, so it now drives a working-stage completion and asserts the provenance-marked block — making it verify both halves of the single-cycle acceptance criterion; a task's claim to "follow the existing test pattern" was corrected (the in-process approach is new and deliberately so); and an instruction that preferred monkeypatching owned code was flipped to prefer the stronger behavior-and-wiring approach, with the mock kept only as a fallback when no configurable cap is exposed.

**Wave structure and rationale.** Wave 1 is the shared fixtures. Wave 2 is the foundation primitives that depend on nothing new — schema, retention, the capture gate with all its hardening, the known-agent set, and the pure token harvester. Wave 3 adds the single event writer and the report, which build on the foundation. Wave 4 is the five producers that write through the writer plus the retrospective injector. Wave 5 is the orchestrator wiring — the `fbk.py` dispatch wrap, the `state.py` injector call, and the installer migration — each interposing on an existing control-flow point and therefore routed to Sonnet with an explicit wiring checklist. Wave 6 is the cross-cutting end-to-end seam, which runs last because it exercises the assembled whole.

## Stage 6: Implementation

**Result.** All 37 tasks completed and verified across 6 waves. Final suite: 336 tests pass, zero failures, zero parks, zero tasks hitting the escalation cap. Baseline was 225 passing tests; the feature added 111 net-new tests (44 in wave 2, 21 in wave 3, ~29 in wave 4, ~16 in wave 5, 2 in wave 6) with no baseline regressions surviving into a commit.

**Per-task outcomes.** Every task passed its paired tests on the first implementation attempt — no task was reassigned, revised-and-retried, or parked. The four tasks routed to Haiku (the schema/redaction/drift tests, the gate-instrumentation tests, the overhead-budget test, and the schema implementation) all succeeded on Haiku with no escalation, so model routing was 100% accurate for this feature. The remaining 33 tasks ran on Sonnet. One task (the fbk.py dispatch wrap) correctly HALTED rather than forcing a pass — see failure attribution.

**In-session retries.** None. No TaskCompleted hook rejection-and-retry cycles were reported by any teammate.

**Task sizing accuracy.** Almost every task touched exactly its declared file scope. Three deviations, all benign: the overhead-budget test task added a 3-line pytest marker registration to pyproject.toml (undeclared, accepted); the verification-persistence task fixed a pre-existing single-vs-double-hash regex bug inside its own declared file (in-scope, beyond the stated change); and the installer task's helper signature differed cosmetically from the test author's prose description (the passing tests are authoritative).

**Team-lead integration fixes (the orchestration's real work).** Five cross-task issues surfaced at wave boundaries that no single task owned; the team lead diagnosed and fixed each, keeping the suite green before advancing:
1. Wave 2 — the drift check flagged environment-variable-name literals (CLAUDE_CONFIG_DIR etc.) and a datetime "Z" as drifted event types, because the schema task implemented it as "any ALL-CAPS literal minus the vocabulary." Narrowed to event-type context (event_type= / build_event( first arg).
2. Wave 3 — registering the report command grew COMMAND_MAP 18->19 and broke a baseline dispatcher test whose update the breakdown had scheduled two waves later (task-18). Pulled that planned assertion change forward to keep the baseline green; narrowed task-18's wave-5 scope accordingly.
3. Wave 4 — the verification-persistence tests used strict-xfail markers that would flip to XPASS-failures the moment the impl worked; converted them to plain red-phase tests so the red->green transition was clean.
4. Wave 5 — the chokepoint integration test ran "state create" as setup through the now-wrapped dispatch, double-recording PIPELINE_COMMAND and failing a "== 1" assertion. Fixed the test to clear the event log after setup so it measures only the call under test.
5. Wave 5 — wiring the retrospective injector into transition_state added a getcwd()-relative side-effect that the pre-existing state tests (which set STATE_DIR but not cwd) leaked into the repo working copy. Added cwd isolation to the shared state-test fixture.

**Verification gate pass rates.** Every wave's test-compile gate passed on the first run (clean collection, expected red/skip profile). Every wave's per-wave full-suite verification passed after the team-lead fix for that wave: waves 2, 3, 4, and 5 each required exactly one integration fix; waves 1 and 6 passed with no intervention. File-scope checks flagged only the documented team-lead fixes and the one accepted marker-registration expansion.

**Wall-clock.** Roughly 90 minutes end to end (first fixture task ~14:10, final seam test ~15:38), with the test and implementation phases of each wave running their tasks concurrently (peak wave width 7 in wave 2's test phase).

**Upstream traceability.** Stage 2 design pre-resolved ten interface contracts, which made implementation largely transcription against a pinned design. Stage 3 breakdown produced 11 compile-time bounce-backs, all resolved without returning to spec, and the checkpoint-2 test review was accepted with 3 applied refinements. Both Stage 3 deterministic gates (task-reviewer, breakdown) passed before implementation began. No blocking finding required a spec revision during implementation.

**Failure attribution (for the five integration issues, since no task escalated).**
- Drift-check false positive: **implementation error** — the schema task explicitly warned that quoting non-event ALL-CAPS literals would break the naive check, and the impl took the naive path anyway.
- Dispatcher count lag: **compilation gap (sequencing)** — the breakdown scheduled the test-assertion update two waves after the code change that invalidates it, which the inter-wave regression gate cannot tolerate.
- Chokepoint setup double-count: **compilation gap** — the integration test was authored with a setup assumption (setup command produces no event) incompatible with the universal dispatch wrap the paired implementation adds.
- Injector cwd leak: **compilation gap** — adding a cwd-relative side-effect to a long-existing function was not accompanied by a task to isolate cwd in the function's pre-existing tests.
- xfail normalization: **not a failure** — a valid test-authoring choice the team lead smoothed to keep the red->green transition unambiguous.

**Outstanding — documentation impact incomplete.** The spec's documentation-impact section lists deliverables the breakdown produced no tasks for, so they remain undone: GLOSSARY entries (capture level, capture gate, event envelope, chokepoint, metrics plane); installer/operator documentation for capture.cfg, the three capture levels, the .fbk-capture/locked/ baseline-lock step, and the human router-activation step; a README/operator capture section; and a retrospective-skill-guide note that a machine-written "## <STAGE> — metrics" section coexists with the agent's prose. Done: the code-review skill gained its .code-review-rounds.json instruction (task-33), and the architecture-overview and decisions-log carried pre-staged edits on this branch. Recommend a short documentation pass (and the README change discussed with the operator per the project rule) before release.

**Process observation for pipeline improvement.** The recurring failure mode this feature exposed is not within-task quality — every task passed first try — but cross-task integration assumptions that only bite when independently-authored test and implementation halves meet, or when a new side-effect/registration collides with pre-existing baseline tests. Four of the five team-lead fixes are of this shape. A breakdown-stage check that (a) keeps a test-assertion update in the same wave as the change that invalidates it, and (b) flags when a new task adds a cwd-relative or global side-effect to a function with pre-existing tests, would have pre-empted the dispatcher-lag and injector-leak issues. The documentation-task omission is a separate breakdown gap worth a coverage check: every documentation-impact bullet in a spec should map to a task or an explicit deferral.
