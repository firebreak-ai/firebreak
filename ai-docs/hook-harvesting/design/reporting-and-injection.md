# Reporting and Injection

What consumes the captured events. One aggregation engine serves two callers: the standalone report command (ad-hoc spot checks) and the deterministic per-stage retrospective injection. A post-hoc token harvester joins transcript data to stages. Parks and rework are derived from the state engine, not from any new event.

## The report command

`python3 fbk.py report <spec>` aggregates all sources into one table and prints it. It is runnable at any pipeline point — no special mode or stage requirement — producing partial rows mid-cycle. It reads:

- `events.jsonl`, filtered to the spec — pipeline-command, verification-result, code-review-rounds, and subagent-stop events.
- The state engine — stage durations (from stage timestamps), parks with reasons (from error history), and rework (from stage re-entry).
- The token harvester output — tokens per stage.

The table rows, at minimum: per-stage duration; gate outcomes as two rows per gate (first-try pass rate, after-rework pass rate); parks per stage with the recorded reason; tasks completed and reworked; scope violations; code-review detection rounds with raised-to-confirmed counts and kill rate; tokens per stage. A missing transcript marks the token row "unavailable" — distinct from a true zero. Where no event of a kind occurred, the row is legitimately empty.

The command also exports `stage_summary(spec, stage) -> str`, which produces the markdown block for a single completed stage. The injector calls this; the command reuses it for the full table. The standalone command does not write to the retrospective — injection is a separate code path (the `--inject` flag from earlier drafts is not implemented).

Module: `fbk/report.py` (flat, matching the existing single-command convention; the earlier `fbk/commands/report.py` was superseded at spec time); registered in `COMMAND_MAP` as `report`.

## First-try vs. after-rework gate rates

A gate attempt is *first-try* if it occurs before any park has happened for that stage in the current entry; *after-rework* if it follows a park and a ready re-entry on the same stage. The classification keys on park boundaries, not on attempt count: if a gate is re-run several times before the work parks, those all fall on the first-try side (the stage entry has not yet been reworked); the first attempt after a ready re-entry begins the after-rework side. The report classifies each attempt by correlating pipeline-command events with the state engine's error history (which records each park's stage and timestamp) and stage timestamps, then reports the two rates separately. This is the operator-chosen behavior: a gate that passes cleanly half the time but always passes after rework reads differently from one that struggles both ways, and a single blended rate would hide that.

## Subagent identity filtering

Claude's runtime emits subagent-stop events for internal helpers (title and suggestion generators) with an empty or unrecognized agent identity. Those events are recorded in the capture file but excluded from any aggregated subagent count or result, so phantom helpers never inflate the metrics. The filter matches the agent identity against the known-Firebreak-agent set (sourced as described in `configuration-and-lifecycle.md`). The filter applies at report aggregation time and, for the hook router, also at capture time for the subagent path.

## State-derived parks and rework

Two rows come from data the state engine already keeps, with no new logging. Parks per stage and their reasons come from the error history. Rework is stage re-entry: when a stage appears in the stage timestamps more than once, the repeated entry marks rework — distinct from a first-pass failure corrected without re-entering the stage. The report reads both directly from the state file. The park reason is whatever free-text string the caller passed at park time — there is no enum or fixed form; any string satisfies the row. A park reason may be an empty string (the state engine stores `reason or ""`); the report renders that as "(no reason recorded)" rather than dropping the row, so an empty reason still produces a visible park row.

## The post-hoc token harvester

Token counts are not visible to the Python layer during a live session. After a session, the harvester reads the session transcript and any subagent transcripts, extracts tokens by type (input, output, cache reads) and by model, counts tool calls and tool errors, and joins them to stages using the state engine's per-stage timestamps. A cycle that spanned several sessions produces one set of per-stage totals, not several disconnected ones.

Stage attribution is a **hard split** on the transition timestamps: each transcript turn — one assistant API response, the record the harvester reads token usage from — is attributed to the stage whose transition timestamp is the latest one at or before the turn's timestamp. A turn whose timestamp is strictly before a boundary goes to the earlier stage; a turn whose timestamp is at or after the boundary goes to the later one. This accepts a small, consistent misattribution at boundaries — acceptable because the table is coarse-grained and the error is identical across compared cycles. When a transcript is absent or unreadable, the affected stages are marked unavailable, never zero.

Module: `fbk/capture/token_harvester.py` (inside the capture subsystem; the earlier `fbk/harvest/token_harvester.py` was superseded at spec time) — a pure reader, ported from the validated prototype's `harvest_session()`. It never writes events.

## Deterministic per-stage retrospective injection

The metrics funnel into the retrospective from code, at every stage completion — not from an operator command and not at agent discretion. The trigger is the state engine's `transition_state()`: after it writes the state file, if the transition is a stage *completion*, it appends that stage's metrics block to the spec's retrospective file.

- **Trigger predicate — precise.** The active working stages are exactly the eight states that can transition to `PARKED` in the state machine: `VALIDATING`, `REVIEWING`, `BREAKING_DOWN`, `TASK_REVIEWING`, `TESTING`, `TEST_REVIEWING`, `IMPLEMENTING`, `VERIFYING`. Injection fires when, and only when, **both** hold: the *previous* state (the one being left) is one of these eight working stages, **and** the *new* state is not `PARKED`. The working-stage half is derivable from the state machine — a working stage is any state whose valid-transition list contains `PARKED` — so the implementation reads that set from `VALID_TRANSITIONS` rather than hardcoding it. The "new state is not `PARKED`" half is essential and was the gap a review caught: a working stage transitions to its checkpoint state on **success** and to `PARKED` on **failure**, and in *both* cases the previous state is a working stage (`state.py` sets `prev_state = current` before writing `new_state`). Keying on the previous state alone would inject a "stage completed" block on every park, when the stage actually failed. The call site therefore passes the local `prev_state`, not the persisted `current_state`, and the injector fires only on the success transition (working stage → its checkpoint). Injection does **not** fire when leaving a checkpoint state (`VALIDATED`, `REVIEWED`, `BROKEN_DOWN`, `TASKS_READY`, `TESTS_WRITTEN`, `TESTS_READY`, `IMPLEMENTED`), nor when leaving `QUEUED`, `PARKED`, or `READY`, nor when a working stage transitions to `PARKED`. This is correct by construction: a stage's metrics exist only once that stage has *finished successfully*, which is exactly the working-state-to-checkpoint transition. It also covers rework for free — when a parked stage is resumed (`READY` → `IMPLEMENTING`) no injection fires on entry; when the redone stage parks again no injection fires; and when the redone stage finishes (`IMPLEMENTING` → `IMPLEMENTED`) both halves of the predicate hold, so the reworked stage's metrics are injected just like a first pass (a second marked block for that stage, distinguished by its provenance timestamp).
- **Path resolution.** `transition_state(spec_name, new_state, reason)` today receives only a spec name and target state; it resolves the state directory relative to the current working directory (the `STATE_DIR` default is the relative `.claude/automation/state`). The injector follows the same convention: it treats `os.getcwd()` as the project root — the same assumption the chokepoint recorder and the report prototype already make — and resolves the retrospective path from there. `transition_state` passes only `spec_name` and the previous state to the injector; the injector resolves the path internally. The exact retrospective filename must be reconciled with the existing `<feature>-retrospective.md` naming at spec time (see `contracts.md`, IF-D-09).
- **Fail-silent.** The whole injection is wrapped in a try/except inside `transition_state()`, after `save_state()`. A failed injection must never prevent a transition from succeeding — the state engine's transitions always succeed; injection is best-effort.
- **Content.** The injector calls `report.stage_summary(spec, completed_stage)` for the deterministically-available rows (duration, gate outcomes, verification, rounds). Token rows are omitted from the injected block because token attribution is post-hoc; the full report supplies tokens on demand.
- **Provenance.** Each block opens with a machine marker, exactly `<!-- fbk-metrics stage=<STAGE> spec=<SPEC> generated=<ISO-8601> -->` (no trailing space), which the success criterion's automated check keys on via a stripped match.
- **Coexistence with agent prose.** The retrospective append function is append-only and reads-before-write. The injector calls it with a metrics-specific heading — the stage name suffixed `" — metrics"` (for example, `## IMPLEMENTING — metrics`) — which is distinct from the plain stage heading the skill instructions use for the agent's interpretive prose. Two entries per stage — numbers under the metrics heading, interpretation under the plain heading — is the expected, correct state; neither append can overwrite the other, and the provenance marker further distinguishes the machine block.

Module: `fbk/capture/retro_injector.py`, exporting `inject_stage_metrics(spec, completed_stage)`. The state engine gains a guarded call to it.

**Relationship to the PRD's auto-injection behavior.** The PRD describes auto-injection as happening "when the retrospective phase runs." Per the operator's design-phase ruling, there is no single retrospective phase and no operator-run retrospective command; retrospective sections are appended at multiple stage boundaries, so injection is wired per-stage into the state transition instead. This per-stage injection is the deliberate, recorded supersession of the PRD's phrasing — not an accidental divergence — and it still satisfies the underlying requirement: the table is machine-written into the retrospective from code, independent of the agent, carrying a provenance marker.
