# Spec review — code-review-exec-path

Perspectives: Architectural soundness (council Architect), Quality (council Guardian), Over-engineering / pragmatism (council Builder), Cross-model GPT-5.5 (external, Codex high-effort)

Four independent passes reviewed the spec against the gate-passed design and the real `pipeline.py`, lenses, skills, and challenger contract. Findings are organized by SDL concern. The headline is a convergent blocking finding raised independently by three of the four passes: the feature's highest-consequence behavior (the verdict-to-finding re-join, where position is the only correlation key) has zero automated coverage, and the spec's "not testable" framing does not hold.

---

## Architectural soundness

**Contract transcription is faithful overall.** Five spec contracts (IF-D-01..05) map one-to-one to the five design contracts; no count mismatch, no orphaned or dropped contract. Both `validate_sighting` production call sites are correctly enumerated, and all asserted function signatures (`load_lens_matrix`, `validate_sighting(finding, vocab=None)`, `normalize`, `cmd_validate`, `cmd_run`, `main()`) exist as stated. Two real transcription gaps remain.

- **blocking — Cited-source injection seam is silently dropped from the rewritten flow.** The shared spine (`review-loop.md` steps 3–4) requires the coordinator to collect the documents named in each candidate's `source_of_truth_ref` and inject them into the challenger spawn; the challenger contract (`fbk-review-challenger.md`, item 4) expects those documents. The spec's seven-stage flow describes only normalized findings reaching the challenger and never mentions cited-source collection/injection. An implementer following the spec literally could remove a locked verification input from every migrated skill. Resolution: add cited-source collection and injection to the per-skill wiring, preserving the challenger's input order — artifact, lens, normalized findings, cited documents, verification instructions.
- **important — IF-D-02 drops the design's "missing fields yield empty strings" guarantee.** Design Contract 2 states a finding missing fields yields a six-field record with empty strings (realized by `normalize()`'s `.get(key, "")` calls). The spec's IF-D-02 invariants omit this, and no test asserts it, so the breakdown agent writing `cmd_normalize` has no spec-level statement that a partial finding must not raise. Resolution: add the invariant ("a finding missing one or more source fields yields empty strings for those fields, never an error") and a unit test.
- **important — Documentation-impact line rests on a false "already defined" premise.** The spec says to "confirm" the terms *composable pipe* and *neutral handoff* are in `GLOSSARY.md` and "add if missing." Both are absent — the parent feature minted glossary entries for researcher/challenger/lens/preset but not these two. Three contracts use them as load-bearing terms-of-art, and project convention requires a glossary entry when a spec introduces a term. Resolution: change the doc-impact line from "confirm/add if missing" to "add glossary entries for *composable pipe* and *neutral handoff*" — these are new term introductions this feature owns.
- **informational — IF-D-05 narrows "rejected and logged" to "rejected."** The design's Contract 5 invariant says out-of-type findings are "rejected and logged"; the spec's IF-D-05 drops "and logged." The `REJECTED:` stderr line is real and survives in AC-07 and the user-facing section, so the guarantee is covered elsewhere. Restore the word for fidelity or accept as covered.
- **informational — Required-field iteration order is unspecified under a lens.** `vocab.required` is a set; `REQUIRED_FIELDS` is an ordered list. The required-field loop returns only the first rejection, so under a lens the specific `missing field '<x>'` message is non-deterministic when more than one is missing. Harmless for the no-lens AC and for the type-rejection message (the enum check runs after the loop), but the breakdown must not write a lens-path test asserting a *specific* missing-field message. Pin any such fixture to omit exactly one required field.
- **informational — `run` double-renumbers, the pipe does not.** Correctly carried in IF-D-05 (non-contiguous `S-NN` on the pipe path). One adjacent asymmetry the spec does not state: `run` renumbers a second time after severity-filter, the pipe path does not. The re-join is id-independent so this is harmless; one sentence would prevent a task author writing a brittle contiguity assertion.

## Quality

The "existing tests impacted" claims are accurate against the real files; the lens-vocabulary assumptions behind AC-01 (id-less acceptance) and AC-07 (the `behavioral`-rejected-under-test-lens catching test) check out and are non-vacuous. The testing strategy has one serious, convergent gap.

- **blocking — The count-guard and positional re-join have no automated coverage, and the "not testable" concession does not hold.** The spec consigns the verdict-count check and position re-join entirely to "skill-orchestration prose" validated only by an operator manual run. But the re-join is a pure two-list transform: given N kept findings, M verdict records, and position, produce either N merged records (overlaying only the four verdict fields plus reclassification) or a named failure when M ≠ N. It has no I/O, no agent, no LLM — exactly as testable as `normalize()` or `cmd_validate`'s renumber, both of which this same spec unit-tests. The behavior is being treated as untestable because of *where it lives* (skill markdown), not *what it does*. This is the integrity boundary of the whole challenge handoff: if the re-join misaligns by one position, a rejected finding inherits a "verified" status and the output looks well-formed. Highest consequence, zero coverage. Resolution: extract the re-join and count guard into a testable pipeline helper (e.g. a `rejoin`/`cmd_rejoin` subcommand, or at minimum a pure `rejoin(kept, verdicts)` function), then cover the happy path, both mismatch directions (N+1, N−1), and the "six neutral fields are not copied back / evidence not double-folded" assertion. If the council keeps it in prose, the spec must justify why a helper the skill *calls* is worse than prose the skill *performs* — it does not attempt that argument.
- **blocking — The verdict-field-overlay selectivity has no test that would catch it breaking.** IF-D-03 states the six neutral fields are never copied back (copying `evidence` would double-fold the location). The spec explains the failure mode but lists no test for it. A manual run will not reliably surface a duplicated `(file:line)` suffix in `evidence`. Resolution: fold into the re-join helper test — assert the merged record's `evidence` equals the kept finding's `evidence` byte-for-byte.
- **important — AC-09's only listed pipeline test is vacuous.** The "challenger array of length N+1/N−1 detected by the count guard" test is filed as covering AC-09, but `cmd_validate` has no count guard — it validates and renumbers each record independently with no notion of expected count. The test passes whether or not the count-guard behavior works. Resolution: replace with the helper mismatch tests above, or strike it and mark AC-09 explicitly as having no automated coverage rather than dressing it with an unrelated `validate` assertion.
- **important — AC-10's verdict-field presence check has no automated test.** The status enum (five values) plus the conditional `verification_evidence` presence rule is a concrete, enumerable validation that `validate --lens` deliberately does not perform (IF-D-04) and no test touches. A verdict with `status: "approved"` or a `verified` finding missing evidence would pass every automated check. Resolution: extract a `validate_verdict(record)` helper with unit tests per rejection case, or state plainly that AC-10's verdict-field half has no automated coverage and accept the risk.
- **informational — Catching-test fixture must be complete-except-for-type.** In `validate_sighting`, the required-field check runs before the type-enum check, so the AC-07 fixture asserting `REJECTED: invalid type 'behavioral'` must be otherwise-valid (all required fields present, min-lengths met) or it rejects on a missing field first. State this in the test plan.

## Over-engineering / pragmatism

The two genuinely-questioned design choices come back clean: keeping code review on `run` while the other three use the composable pipe is the right pragmatic call (forcing code review onto the pipe would require inventing a preset-less domain filter — strictly more change), and the non-contiguous-id difference is genuinely cosmetic (nothing downstream reads `S-NN` for meaning; position is the correlation key). Declining the same-length-reorder hardening is correctly priced. Not adding preset entries is the right anti-duplication call. Three real gaps remain.

- **blocking — "Extend" misrepresents the three-skill work; those skills have zero executable pipeline wiring today.** A grep of the test, coherence, and task review skills for `pipeline`/`normalize`/`validate --lens`/`severity-filter` returns nothing executable — all three describe the loop purely in prose and route to the abstract spine. Only code review has concrete `fbk.py pipeline` calls. The spec frames the three-skill work as repointing/adding calls "to gain the same shape," as if a pipeline invocation already exists to modify. In reality each skill must be converted from prose orchestration to executable orchestration for the first time — the detection command, the normalize step, the re-join with count guard, and the re-validate, none of which exist in any form. "Reopens currently-green code" undersells it: there is no green executable code, there is prose being replaced by steps that have never run. Resolution: rewrite the three skills' module-touch entries as "convert prose loop to executable wiring," state that no pipeline command exists in them today, and have the operator choose with the true cost named — either split the three-skill conversion into its own slice, or de-scope the sweep from this merge-prerequisite and land only the code-review fix that unblocks the branch.
- **important — The single `finding-mode-skill-migration` slice is too coarse, and has an AC-traceability gap.** One `cross-cutting` slice bundles four skills, two execution shapes, and four distinct behaviors, mixing code review's contract-preserving guarantee (report/history shape unchanged) with three brand-new orchestration flows. AC-11 (code review's wiring change) is not in the slice's `covers` list, yet code review's change lives there. A task compiler must invent the task boundaries. Resolution: split into a `code-review-lens-repoint` slice (covers AC-08/09/10/11, mixes new-contract and contract-preserving) and a `three-skill-executable-migration` slice (covers AC-07/08/09/10/12); optionally a shared re-join/count-guard slice.
- **important — The `reclassified_from` overlay rule is left for the implementer to invent.** The challenger returns `type`/`severity` on every record (the normalized input already carries them) and signals a real change only via `reclassified_from` being non-empty. IF-D-03 says to overlay "the changed `type`/`severity`" without stating how the orchestrator distinguishes changed from unchanged. Resolution: pin the rule — "overlay `type`/`severity` from the challenger record only when its `reclassified_from` is a non-empty object; when it is `{}`, retain the kept finding's original classification." Also add a concrete seven-stage step template the three skills adopt, and name where it lands in each skill document.

## Cross-model GPT-5.5

The external high-effort pass confirmed the function signatures and the two call sites, and confirmed the four lenses' id-less required sets. It independently raised the two blocking findings above (skill-orchestration ACs untested; cited-source injection dropped) and added four precision findings.

- **important — `run --lens` is under-tested.** AC-01/03/04 require both `validate` and `run`, but the new-tests list gives only `validate --lens` cases. The most important code-review path is `pipeline run`; `validate`-only tests can pass while `cmd_run` mishandles `--lens`. Resolution: add subprocess tests for `pipeline run --preset behavioral-only --min-severity minor --lens code-lens.md` accepting an id-less finding, plus missing- and malformed-lens cases for `run`.
- **important — "Empty input" contradicts the chosen implementation.** `cmd_normalize` uses `read_stdin_json()`, which exits non-zero on a JSON decode error. Zero-byte stdin is malformed JSON; JSON `[]` is an empty list. AC-06 and Contract 2 say "empty input exits zero" while the test says `[]` — two meanings. Resolution: pin the wording to "JSON empty array `[]`" unless zero-byte stdin is intentionally special-cased.
- **important — "Byte-identical" is narrowed to stdout only.** Design requires byte-identical no-lens behavior; AC-02 pins only stdout. The pipeline emits meaningful stderr warnings (the 30%-rejected warning) and exit codes. A change altering warnings or exit codes would violate the design but satisfy the AC. Resolution: AC-02 should compare stdout, stderr, and exit code for both `validate` and `run`.
- **informational — "Same content" overclaims.** The user-facing section says code review stops returning empty *and* that the report keeps "the same shape and content." Content cannot be unchanged if previously-rejected id-less findings now surface. Resolution: say "same schema/format, no new fields," not "same content."
- **informational — Test fixtures should be repo-relative.** The test plan says tests "load the real installed lenses." CI tests should not depend on `$HOME/.claude` install state. Resolution: load repo-relative lens assets under `assets/fbk-docs/fbk-review-lenses/`. (The skills' runtime `--lens` paths stay installed-absolute; only the tests change.)

## Threat model determination

**Decision: no threat model.** Rationale: this feature introduces no new trust boundary in the security sense, no authentication or authorization change, no data storage, and no external API or network interaction. It changes a local validation/normalization command-line program and the review-skill documents that drive it; all inputs are developer-supplied findings already inside the pipeline. The one "isolation"-flavored property in play — the challenger seeing only six neutral fields — is a review-quality invariant, not an external attack surface, and is covered by the normalization contract and the cited-source finding above. Security agent was not invoked; security-relevant characteristics were summarized and found absent. (Operator confirmation pending at synthesis time.)

## Testing strategy coverage

The review confirms the spec's testing strategy carries all three required categories, with the coverage gaps noted above as blocking/important findings to resolve before the gate.

- **New tests needed** — present. Lens-required-set acceptance, byte-identical default path, missing/malformed-lens CLI behavior, `normalize` six-field/order and empty/non-JSON cases, and the three per-type catching tests are enumerated. Gaps to add (from findings above): `run --lens` acceptance and failure cases; the re-join helper happy-path and N±1 mismatch tests; the evidence-not-double-folded assertion; the verdict-field presence check; and the `normalize` missing-field-empty-string assertion.
- **Existing tests impacted** — present and verified accurate. `test_pipeline_backward_compat.py` (default path, stays green under `vocab=None`), `test_pipeline_normalize.py` (per-finding `normalize()`, additive subcommand cases), `test_pipeline_missing_lens.py` (function-level raise; add CLI-wrapping cases — note its stale "AC-06" docstring reference from the parent feature), `test_pipeline.py` (no fixed-arg-count assertion; backward-compatible). 
- **Test infrastructure changes** — present. Real installed/repo-relative lenses plus a malformed-lens fixture; no new framework. Change requested: repo-relative lens paths rather than `$HOME/.claude` install state.

## Independent test-review — two passes, reconciled

Two independent test-quality passes ran against the stabilized spec.

- **In-pipeline test-reviewer (authoritative artifact, `test-review-spec.md`): `accepted`.** It confirmed the re-join extraction is the right call and its planned tests genuinely catch (the kept finding's `evidence` byte-identity and the overlay-selectivity / reclassification rules would fail if the implementation copied neutral fields back or mis-applied `reclassified_from`). It accepted, as honestly-declared limits rather than hidden gaps, that the skill-conformance greps prove text-presence (not execution) and that the verdict-field presence check (AC-10) is prose-only by the design lock. Two non-blocking recommendations: anchored structural markers in the skill greps, and a chained subprocess test across `validate | severity-filter | normalize | rejoin`.
- **Cross-model GPT-5.5 (Codex high-effort): `needs-revision`, three blocking + four important.** It agreed the re-join is testable and the catching tests are sound, but found the planned `rejoin` tests under-rigorous on the highest-consequence property: the happy-path test needed ≥3 findings with distinct sentinels to catch a reversal or constant-index overlay (not just N±1 counts), and the neutral-field assertion needed all six fields, not only `evidence`. It also pushed the chained-integration gap from "future" to "now," and wanted AC-03/04 tests to prove *ordering* (lens fails before any finding is read), not just message text.

**Reconciliation:** the two passes did not actually conflict on substance — they differed on how rigorous the *test specification* must be and on the timing of the chained-integration test. Every concrete Codex strengthening was folded into the spec's testing strategy: position-rigor happy-path (≥3 distinct sentinels, exact index-to-index), all-six-neutral-fields protection, `reclassified_from` preservation assertion, AC-03/04 ordering proof, AC-02 golden stdout/stderr/exit, anchored skill-grep markers, and a chained-integration subprocess test through the real command sequence.

**Verdict-field enforcement adopted (operator-confirmed 2026-06-24).** The one Codex point initially held back — tool-enforcing the verdict-field check — was discussed with the operator and adopted, as a *separate* `pipeline validate-verdicts` subcommand (new contract IF-S-03, AC-15) rather than folding it into `rejoin`. This supersedes the design's "verdict check stays prose" lock: a verdict with an invalid status now fails loudly instead of silently dropping a confirmed finding at the verified filter. The change is additive tool-enforcement plus tests, closing the one accepted prose-only gap. The spec was re-revised, re-passed the spec gate, and the independent test-reviewer was re-run against the final spec.

**Final test-review verdict: `accepted`** (re-run against the revised spec). The reviewer confirmed the `validate-verdicts` tests are non-vacuous (the `approved`-status silent-loss case pins the exact failure the subcommand prevents), that AC-10 now has both halves enforced with no prose-only gap, and that no prior coverage (re-join, lens/normalize, catching, chained-integration) was weakened. The only residual on the manual-QA tier is live agent-spawning execution (UV-3); every command-level guarantee below the agents is automated.
