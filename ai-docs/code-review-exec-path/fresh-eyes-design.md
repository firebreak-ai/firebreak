# Fresh-eyes design review — code-review-exec-path

Two independent cold passes on 2026-06-24: an isolated in-pipeline reviewer and a cross-model pass (GPT-5.5, high reasoning effort, via Codex). Both read the actual `pipeline.py`, the four lenses, the four review skills, the challenger agent, and `review-loop.md` as source of truth. The cross-model findings and their resolutions are recorded under "Cross-model pass (GPT-5.5)" below.

## Summary

The in-pipeline pass raised three Critical, six Important, and three Minor observations. The cross-model pass raised two Critical and two Important — and crucially caught inconsistencies introduced by the first round of fixes (a contract that still held the broad merge formula after the prose was narrowed; a contract that still asserted same-order as a guaranteed invariant; a fail-open count check; a tool claimed to validate verdicts when it validates only finding fields; an overclaim that the feature lights up scan-mode routing). All real findings from both passes were resolved in the design revision of 2026-06-24.

## Critical

No open critical observations remain after the 2026-06-24 revision. Five Criticals were raised across the two passes; their triage and resolution are in the resolution logs below. In short, from the in-pipeline pass: two described the current code, which Contract 1 explicitly rewrites (the design now states the call-site edits plainly rather than calling them plumbing); the third (post-challenge re-validation described as a "pure check") was a true inaccuracy, now described as a filter-and-renumber that runs after the re-join. From the cross-model pass: the broad merge formula left in Contract 3 was narrowed to a verdict-only overlay matching the prose, and the positional re-join's reorder gap is now stated in Contract 3 as a known limitation rather than asserted away.

## Important

- **Positional re-join cannot detect a same-length reordering.** The count check catches a dropped or inserted verdict but not a shuffle; with position as the only key, a reordered array mis-joins every record silently. **Resolution:** documented as a stated known limitation in the handoff page, with the low-likelihood rationale (the challenger reads cold, is instructed same-order, has nothing to reorder by) and a hardening option (an opaque echoed index token) recorded as an open item for the spec phase. Not hidden behind the count check.
- **The "can't use `run`" reason was incompletely stated.** The design gave "no preset entry" as the whole reason; the reviewer wanted the type-filtering rationale made explicit. **Resolution:** the composable-pipe page already grounds the choice in the lens being the single type-filter authority and warns against adding preset entries; the reorder/severity clarifications were added alongside. Verified that with `--lens` on `run`, the deeper "type-rejection" the reviewer hypothesized does not occur — so the operative reason genuinely is the preset-file requirement.
- **The two command paths are not fully identical, but the design implied they were.** Code review's `run` renumbers ids after filtering; the composable pipe's `severity-filter` does not, yielding non-contiguous ids. **Resolution:** the composable-pipe page now states the guarantees are identical while two observable behaviors (id numbering, and that severity *threshold* filtering is built-in not lens-governed) are not, removing the "identical" overstatement.
- **The two-defect framing blurred which call X-1 breaks.** X-1 is the detection-round validation (before ids exist), not the post-challenge call. **Resolution:** overview and a new handoff subsection now pin X-1 to the detection-round call and state separately why stage 6 changes.
- **Lens-declared severities are enforced at validation, not by `severity-filter`.** The reviewer noted the `info`-severity mismatch across lenses and that the threshold filter is built-in. **Resolution:** the composable-pipe page now distinguishes lens-as-type/severity-validity authority (enforced at `validate --lens`) from the fixed threshold ordering used by `severity-filter`.
- **The "default no-lens path is byte-identical" claim coexists with a caller (code review's current step 5) that relies on it.** **Resolution:** the design moves that step-5 call onto `--lens` and the handoff page now explains the current step-5 call works today only because ids exist by then — so the claim and the migration are consistent and the broken call (detection round) is named precisely.

## Minor

- **Evidence double-tagging in the merge.** Overlaying the whole normalized record re-applied the folded location into evidence on top of the original. **Resolution:** stage 5 now overlays only the verdict fields plus any reclassified type/severity, never the six neutral fields, so the original evidence and structured location are untouched.
- **`normalize()` is per-finding, not per-list.** **Resolution:** Contract 2 now says the new `cmd_normalize` wrapper reads the list and applies `normalize()` per record, including the read-error path, rather than "delegating to the existing function."
- **The clean missing-lens error is new, not inherited.** No command calls `load_lens_matrix` today. **Resolution:** the lens-wiring page and Contract 1 now state the command must wrap the load to exit non-zero with the named message, calling it new command-line behavior rather than inherited.

## Resolution log — criticals

- *Critical 1 — "the call sites already thread a vocab" framing.* The functions accept a vocab, but `cmd_validate`/`cmd_run` call `validate_sighting(s)` with none. The design now says explicitly (lens-wiring page and Contract 1) that the fix edits three places — add the option, load the lens once, and change the call sites — not just CLI plumbing.
- *Critical 2 — "`cmd_validate` ignores the lens, so Contract 4 / the pipe will reject everything."* This describes today's code; Contract 1 adds `--lens` to `cmd_validate`. Contract 4 now states its dependency on Contract 1 explicitly so the post-change behavior is unambiguous.
- *Critical 3 — "stage-6 re-validation is a filter-and-renumber, not a pure check."* Genuine. Stage 6 and Contract 4 now describe `cmd_validate`'s drop-and-renumber behavior, note the re-join precedes it so correlation holds, and note `F-NN` assignment follows so the `S-NN` renumber is invisible.

## Cross-model pass (GPT-5.5, high effort)

- *Critical A — Contract 3 still held the broad merge `{**kept[i], **verdict[i]}` after the prose was narrowed, re-introducing the evidence/location double-handling.* Genuine inconsistency introduced by the first fix round. **Resolution:** Contract 3 now specifies a verdict-only overlay (status, verification evidence, rejection reason, adjacent observations, plus reclassified type/severity), never copying back the six neutral fields.
- *Critical B — positional re-join is not enforceable against a same-length reordering, yet Contract 3 asserted same-order as an invariant and defined only count-mismatch handling.* Genuine. **Resolution:** Contract 3 now carries an explicit "position is not reorder-proof" known-limitation paragraph. The operator reviewed the limitation and locked position-only (2026-06-24), declining the echoed-index-token hardening this iteration — so the limitation is accepted by decision, not left dangling.
- *Important — count-mismatch handling was fail-open (Contract 3 said surplus verdicts are "log and ignore").* Genuine. **Resolution:** Contract 3 now fails the handoff on any count inequality in either direction; surplus means the challenger invented records, which violates the no-new-objects rule.
- *Important — `pipeline validate --lens` does not validate verdict fields (status/evidence); the real `cmd_validate` checks only finding fields.* Genuine — Contract 4 implied a verdict guarantee the tool does not give. **Resolution:** Contract 4 now states the command validates finding fields and the matrix only, and the verdict-field presence check stays a separate prose step in each skill, exactly as code review does today.
- *Important — Contract 1 overclaimed that the feature makes scan-mode routing real at runtime, but scan mode is out of scope and `load_lens_matrix` does not parse the output mode.* Genuine overclaim. **Resolution:** Contract 1's realizes line now scopes the claim to per-lens finding validation and explicitly disclaims scan-mode routing.

Process note: the cross-model pass earned its place — it found defects the first pass cleared, several of them inconsistencies the first round of fixes had introduced. This is the cross-model-as-diversity-axis value the unified-review-shape feature exists to unblock, demonstrated again on this follow-on's own design.
